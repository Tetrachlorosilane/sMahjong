# GPU 自对弈前向 · 可行性判定（唯一门槛 = 确定性）

侦察 2026-10-11 · 只跑小规模前向对拍与普查（**未跑 PPO/训练/闸门/大采集**）· **仓库零改动**（只读他人产物；本文件落 S:）。口径：A0 = `tools/build/v4-wl-dec6170-4g-c2-g04/net.bin`（1.40 M 参数）· OMP/MKL=4 · 一次一个重负载（兄弟 1000 场 w=8 采集跑完后才开跑）。对拍跑在 **`f670777`（大明杠修复后）** 上。
## 0 判读（按任务先写死的尺子）
- 尺子：翻转率 **0/10 万 ⇒ argmax 型自对弈可用 GPU 批**；>0 ⇒ 逐局分岔 ⇒ 不可用（除非接受"新基线"并重建方法论）。
- 读数：**三条轴全 0** —— 设备轴（cpu 批 ↔ cuda 批）**0/121,120** · 批处理轴（batch=1 ↔ batch=512）**0/24,224** · **端到端（C++ 逐行 ↔ GPU 批）0/121,120**（maxΔ 9.2e-5）⇒ **argmax 型可以上 GPU，判据达标**。
- ⚠ 同一普查在**修复前**（`9451690`）端到端是 3/121,120、maxΔ **3.797**、469 行 Δ>1e-4（**全部** `claim` 且候选 ≥3）。根因就是同事在 13,408 行里抓到的那条：`features.py` 的 `action_parts` 把 `kan:daiminkan:a+b+c` 只拆 2 段（`f670777` 改成拆整个键）。⇒ 我的 121,120 行普查在 **469 行**尺度上**独立复现并确认了修复**；修复后 maxΔ 落到 9.2e-5、翻转归零。
- ⚠ **0 观测 ≠ 0 概率**：95% 上界 ≈ 3/121,120 = **2.5e-5/决策**；673 决策/场 × 1000 场 = 67.3 万决策 ⇒ 最坏 ~**17 场/1000** 分岔。⇒ **"同种子 ⇒ 逐字节相同"必死**（maxΔ 9.2e-5 ≠ 0），能保住的只有"同种子 ⇒ 统计可复现"，而这额外要求**批组成确定**（§7-1）。
## 1 翻转率普查（方法 / 规模 / 原始输出）
样本：自采 180 场 **on-policy** 真实对局（`trainer selfplay 180 --workers 4 --policy net:A0 ×4 --seed 900301`，63.1 s）⇒ 2,012 小局 / **121,120 决策行**；sidecar 走 `trainer features`（2.3 s）；张量走 `blocks.assemble`，`h0` 走 `cache.carry_prefix`（"窗口之前 carry"的唯一口径）。三臂 = C++ `v4net` 逐行（4 分片 ×2 遍）· torch CPU 批 512 · torch CUDA 批 512（`--repeat 2`）。

| 对拍 | 行数 | **翻转** | 翻转率 | maxΔ | Δ p50 | Δ p99 | 翻转行 Δ |
|---|---|---|---|---|---|---|---|
| **C++ #1 ↔ C++ #2**（同实现两次） | 121,120 | **0** | 0 | **0.000e+00** | 0 | 0 | — |
| **py-cpu-b512 ↔ py-cuda-b512**（设备轴） | 121,120 | **0** | 0 | 8.39e-05 | 9.5e-06 | 3.1e-05 | — |
| **py-cpu-b1 ↔ py-cpu-b512**（批处理轴，等距子集） | 24,224 | **0** | 0 | 4.58e-05 | 3.8e-06 | 1.5e-05 | — |
| **C++ 逐行 ↔ GPU 批**（端到端，全量） | 121,120 | **0** | **0.0000%** | 9.21e-05 | 9.6e-06 | 3.4e-05 | — |
| **C++ 逐行 ↔ GPU 批**（同子集，逐行对照） | 24,224 | **0** | 0 | 9.16e-05 | 9.6e-06 | 3.4e-05 | — |

- **对照方法本身无假阳性**：C++ 两次 maxΔ **恰为 0**、翻转 0；`--repeat 2` 也断言 CUDA 两次 argmax 逐行相同 ⇒ GPU 前向**同批同结果**。
- 翻转只可能发生在"近平分"处：margin p1 = 7.6e-3、**<1e-5 的只有 5 行（<1e-6 的 2 行）** ⇒ 0 翻转不是"没有近平分行"，而是那些行的 Δ（≤9.2e-5）还没跨过去。
## 2 判读（一句话）
**argmax 型自对弈"可以"上 GPU**：121,120 行真实 on-policy 状态上端到端 0 翻转，maxΔ 9.2e-5 与"换设备"轴（8.4e-5）同量级 —— 即**批 GEMM 与逐行 GEMV 的差别被 argmax 完全吸收**。但"零风险"不成立：必须 (a) 判据从"逐字节"改成"argmax 全同 + maxΔ ≤ tol"（现成形态 `tools/trainer-v4-parity.mjs:11`；⚠ 容差要**随量纲走**，绝对 1e-5 比 fp32 在 |logits|≈30 的 1 ulp 还小）、(b) **批组成确定**，否则 `--workers`/重跑对拍与域掩码"域外逐字节"当场失效。

## 4 CPU 侧零语义收益：整手事件 GRU（复核 20% + 增量 carry 估算）
- **复核（`v4bench`，我自采 g0，n=836）**：事件 ≤8 → **1.611** ms/行 · 9..23 → 1.712 · ≥24 → **1.919**（前向净）；**固定候选数 nlegal=12** 解耦候选数后 ≤8 → 1.631 · ≥24 → **2.018** ⇒ Δ=0.387 ms / Δevents≈31 ⇒ **≈0.0125 ms/事件**；生产均值 26.6 事件 ⇒ 事件流 ≈0.33 / 1.79 ms = **18.6%**（同事报 20%，一致）。
- **上界与估算（MAC 分解，`TRAINER-CPP.md §6.24`）**：GRU 5.0/42 = **11.9%**；`event.enc`+`in_proj`+GRU 14.9/42 = **35%**（该节自报"逐行缓存 ⇒ 1.4–1.5×"）⇒ **只缓存 GRU 隐状态**（每决策从 `events` 步降到 1–4 步）省 **≈12–19% 前向** ⇒ 端到端（前向占 ~90%）**≈11–17%**：12,000 场 1.2–2.0 h → **约 1.0–1.7 h**。
- **判据（AGENTS §6.5 原样）**：增量事件缓存"判据必须**成对** —— 增量 == 全量（**逐位**）*且* 真的命中"；回归 `SelfTest.v4CacheTests` + `tools/v4-cache-check.mjs`。**Java 侧已有**（`--no-v4-cache` 关）、**C++ 侧没有**（`v4policy.cpp:1024`："增量 = 槽里的 `s.h`（Java 侧，C++ 无缓存）"）。
- **风险**：① 必须逐位 —— 实测 carry 对 logits 的影响只有 **≤1.9e-6**（60 步窗口把初始 carry 忘掉 + `fusion.mem` 是小 tanh 门），**影响小 ≠ 免逐位判据**（W1 起 `h_evt` 被融合消费）；② 前缀校验漏判会带上一局的 carry（`cache.py:249`）；③ 要改 `trainer/src` ⇒ 本任务边界外，只报数不动手。

## 6 结论与建议（三选一）—— 建议 **①**，不建议"都不动"（~90% 的墙已证可翻越，CPU 侧只剩 §4 的 11–17%）
| 选项 | 成本 | 收益 | 判据 |
|---|---|---|---|
| **① argmax 型上 GPU（推荐）** | 跨局批调度器（**批组成确定**）+ torch 前向 + 判据改成"argmax 全同 + 随量纲的相对 maxΔ" | GPU 热 23,259 行/秒 vs C++ 单线程 381 行/秒 = **61×/线程** ⇒ 12,000 场 1.2–2.0 h → **10–20 min** 量级 | (a) 同种子同批 ⇒ logits 逐位相同；(b) 121,120 行端到端 argmax 全同（已测 0 翻转）；(c) 新口径下重跑 `--workers`/域掩码对拍 |
| ② 只做 CPU 优化（§4 增量 carry） | 改 `trainer/src`（Java 侧有同款可照搬）+ 逐位判据 | 端到端 **11–17%**（12,000 场 −10~20 min） | 增量 == 全量（逐位）且真的命中（AGENTS §6.5） |
| ③ 都不动 | 0 | 0 | — |
## 7 残余风险 / 缺口
1. **批组成确定性 = 头号风险**（远大于 GEMM/GEMV）：batch 若由到达时刻/线程调度决定，同一 seed 两次跑出不同结果 ⇒ 域掩码"域外逐字节"、`--workers` 对拍、配对读数全部失效；必须由 (game, seat, step) 固定排序 + 固定分桶给出。
2. **"逐字节"必须显式退役**（不许"先放宽再补证"）：0 翻转只是 121,120 行的观测，上界 2.5e-5/决策 ⇒ 1000 场最坏 ~17 场分岔；`<1e-6` 间距的行确实存在（2 行）⇒ 更大样本或更近的平分必然翻。
3. 顺手发现（同事的工具，本次未改）：`tools/v4-forward-gpu.py:831` 在 `--rows <npz> --index-file` 时对 `rows.steps is None` 取下标 ⇒ `TypeError`（在 `forward` **之后**才炸，`[fwd]` 照打而输出文件不存在）；我改用"子集 npz"绕过。
4. 未测：真"跨局批"调度器（本仓没有）、w>8 曲线、教师/风格桌混合策略下的翻转率（本样本只有 `net:A0`×4）；算力账 = 采集 2×63 s + features 2.3 s + C++ v4net 4×~76 s + torch CPU 2×41 s + CUDA 2×20 s + 子集 b1 2×108 s ≈ **14 min**（多个独立重负载，串行、独占）。
