# 自定义输入 JSON 牌谱的格式说明

本文说明 `mjai-reviewer` **唯一接受的自定义输入**——也就是 tenhou.net/6 格式牌谱 JSON——是如何组织的，
以及手写 / 改造这类牌谱时必须满足的约束。

内容全部对照源码核实：

| 用途 | 源码位置 |
| --- | --- |
| 顶层与每局的反序列化结构 | `convlog/src/tenhou/json_scheme.rs` |
| RawLog → `Log`（规则推导、结果解析） | `convlog/src/tenhou/log.rs` |
| 牌码 / 鸣牌串 → mjai 事件 | `convlog/src/conv.rs` |
| tenhou 牌码 ↔ 内部 `Tile` | `convlog/src/tenhou/tile.rs`、`convlog/src/tile.rs` |
| 局过滤 `-k` | `convlog/src/kyoku_filter.rs` |

示例取自 `convlog/tests/testdata/*.json`。

---

## 1. 输入方式与前置约束

```console
$ mjai-reviewer -e mortal -i log.json -a 3      # 本地文件
$ cat log.json | mjai-reviewer -e mortal -a 3   # 标准输入（-i - 亦可）
```

- **格式就是 tenhou.net/6 牌谱 JSON**。`-i` / stdin / `-t`（天凤 log ID）/ `-u`（天凤 URL）四条路径
  最终都汇入同一个反序列化入口（`src/main.rs` 中 `json::from_str::<RawLog>`），
  所以自定义牌谱与从天凤下载的牌谱**必须完全同构**，不存在另一套“简化输入格式”。
- `-a ID` **必填**（0–3，也就是东起手 0、下家 1、对家 2、上家 3）。也可以用 `-n NAME` 按名字定位；
  只看不评（`--no-review`）时可以省略。
- `mjai` 格式**不是**输入格式。`--mjai-out` 只是输出转换结果，不能反向喂回来。
- 引擎限制：**Mortal 只支持半庄（南入）**；`rule.disp` 含 `東` / `East` 会被判为东风战，配 Mortal 会直接报错。
- 三麻不支持（`rule.disp` 含 `三` 或 `3-Player` 直接报 `not four-player game`）。

## 2. 顶层结构

```jsonc
{
  "log":  [ /* 每个元素 = 一局（kyoku），见第 3 节 */ ],
  "name": ["Aさん", "Bさん", "Cさん", "Dさん"],   // 必填，恰好 4 个
  "rule": {                                        // 字段本身必填，但内部各子字段均可省略（省略即默认值）
    "disp": "特南喰赤",                            // 规则名，用于判定 三麻 / 东风战；省略则默认半庄、四麻
    "aka": 0, "aka51": 1, "aka52": 1, "aka53": 1   // 赤 5 枚数：aka=三麻用，aka51/52/53=万/筒/索，省略即 0
  },

  // 以下全部可选，解析器会读入但不参与转换（缺省即不序列化）
  "ratingc": "PF4", "lobby": 0,
  "dan": ["四段", "四段", "九段", "四段"],
  "rate": [1912.87, 1943.31, 2104.6, 1904.95],
  "sx": ["F", "F", "M", "F"]
}
```

另外，来自天凤的原始文件里还会有 `ver`、`ref`、`title`、`sc` 等字段：
`RawLog` **没有** `deny_unknown_fields`，未知字段一律忽略，可以放心保留。

从 `rule` 推导出的三件事：

| 判定 | 条件 | 影响 |
| --- | --- | --- |
| 三麻 | `rule.disp` 含 `三` 或 `3-Player` | 拒绝解析 |
| 东风战 | `rule.disp` 含 `東` 或 `East` | Mortal 拒绝复盘 |
| 有赤牌 | `aka + aka51 + aka52 + aka53 > 0` | 生成 `StartGame.aka_flag` |

> `log` 必须是数组且字段名就叫 `log`；直接喂一个裸数组（某些工具导出的形式）不会被接受。

## 3. 每局（`log` 的元素）

每一局是**位置固定的 17 元组**（`RawKyoku`，用 `serde_tuple` 反序列化），顺序如下：

| 下标 | 字段 | 类型 | 含义 |
| --- | --- | --- | --- |
| 0 | `meta` | `[u8; 3]` | `[局序号, 本场, 供托]`，**局序号从 0 开始**（0=东1，1=东2 … 4=南1，7=南4） |
| 1 | `scoreboard` | `[i32; 4]` | 本局开始时 4 家点数（0..3 号位） |
| 2 | `dora_indicators` | 牌码数组 | 宝牌指示牌；**第一个元素必填**，追加杠宝牌时依次追加 |
| 3 | `ura_indicators` | 牌码数组 | 里宝牌指示牌；和了时整组写入 `Hora.ura_markers` |
| 4 | `haipai_0` | 13 个牌码 | 0 号位配牌 |
| 5 | `takes_0` | `ActionItem[]` | 0 号位“取”（摸牌 / 鸣牌 / 立直宣言） |
| 6 | `discards_0` | `ActionItem[]` | 0 号位“出”（打牌 / 暗杠 / 加杠 / 立直宣言） |
| 7–9 | | | 1 号位，同上 |
| 10–12 | | | 2 号位，同上 |
| 13–15 | | | 3 号位，同上 |
| 16 | `results` | 见第 7 节 | 和了 / 流局的结果声明 |

推导规则（`conv.rs`）：亲家 = `meta[0] % 4`；场风 = `meta[0] / 4`（0=东，1=南，2=西，3=北）；
`StartKyoku.kyoku` 写回 1–4（`meta[0] % 4 + 1`）。

**码位（seat）固定**：下标 0 号位就是开局坐东的那家，全程不变，不随局数轮转。

> 用 `serde_tuple` 从 JSON 数组反序列化：**前 17 个位置必须严格对齐**，多余的尾部元素会被忽略
> （天凤原始牌谱就是 17 个元素；`convlog/tests/testdata/` 里的全部用例也都是 17 个）。
> 少一个元素、或把 `haipai` 写成 12/14 张都会直接解析失败。

## 4. 牌码（tenhou 整数码）

所有牌都用**整数**表示（`TenhouTile`，`repr(u8)`）：

| 码 | 含义 | 码 | 含义 |
| --- | --- | --- | --- |
| `0` | 未知牌（`?`） | `41`–`47` | 东 南 西 北 白 发 中 |
| `11`–`19` | 1m–9m | `51` | 赤 5m（`5mr`） |
| `21`–`29` | 1p–9p | `52` | 赤 5p（`5pr`） |
| `31`–`39` | 1s–9s | `53` | 赤 5s（`5sr`） |
| | | `60` | **仅用于 `discards`**：摸切占位符 |

也就是“十位=花色、个位=数字”：`14` = 4m，`27` = 7p，`36` = 6s，`46` = 发。

不支持的其他牌码（例如 `40`、`48`、`50`、`54`、`99`）会导致解析失败。

命名对照（内部 `Tile` 的字符串形式，`--mjai-out` 输出里用的就是它）：

```
1m 2m 3m 4m 5m 6m 7m 8m 9m
1p 2p 3p 4p 5p 6p 7p 8p 9p
1s 2s 3s 4s 5s 6s 7s 8s 9s
E  S  W  N  P  F  C
5mr 5pr 5sr        # 赤 5
?                  # 未知
```

## 5. `takes` / `discards` 的元素（`ActionItem`）

`ActionItem` 是**无标签联合**，按以下顺序尝试（`json_scheme.rs` + `conv.rs`）：

1. **数字** → 牌码（第 4 节的表）；
2. **数字 `60`** → 摸切标记。在 `takes` 里出现是**错误**（`tsumogiri should not exist in discard table`），
   只有 `discards` 能用；
3. **字符串** → 鸣牌 / 立直标记（第 6 节）。

### 5.1 `takes`（取）

| 元素 | 产生的 mjai 事件 |
| --- | --- |
| 牌码（如 `22`） | `Tsumo { actor, pai }` |
| `"47p4747"` 等 | `Chi` / `Pon` / `Daiminkan`（见第 6 节） |

即：**字面牌码 = 自摸到这张牌**。

### 5.2 `discards`（出）

| 元素 | 产生的 mjai 事件 |
| --- | --- |
| 牌码（如 `22`） | `Dahai { pai: 22, tsumogiri: false }`（手切） |
| `60` | `Dahai { tsumogiri: true }`，**`pai` 稍后由同一手 `Tsumo` 回填** |
| `"r21"` / `"r60"` | `Reach { actor }` **+** `Dahai { pai: 21 或回填后的摸牌 }` |
| `"3636k3636"` | `Kakan { ... }` |
| `"424242a42"` | `Ankan { ... }` |

**注意两点**：

- 立直宣言在 `discards` 里占**一个**元素，但会产生**两个**事件（`Reach` + `Dahai`）；
  `r60` 表示立直宣言牌是摸切。
- 大明杠（`m`）在 `takes` 里，**不产生 `discards` 元素**，所以某家的
  `len(takes) > len(discards)` 是正常的（例如 `complex_nakis_0.json` 的 3 号位：takes 14 / discards 13）。

### 5.3 对齐关系（`finalize_discards`，`conv.rs`）

转换器按顺序遍历该家的 `takes`，并推进 `discards` 的下标：

1. 遇到 `Reach` 就先跳过一个 discard 元素（因为立直已配了自己的宣言牌）；
2. 若当前 discard 是 `60`（摸切），把同一手 `Tsumo` 的牌回填进去；
3. 若当前 discard 是 `0`（未知牌），说明这是大明杠留下的空位 —— 删掉这个 discard 元素，继续对齐；
4. 其余情况两者一一对应。

**因此自造牌谱时要保证**：同一家的 `takes` / `discards` 按真实时间顺序交错排列，
且除大明杠外一一对应；`60` 只能出现在 `discards`，且必须有对应的一手 `Tsumo` 可供回填。

## 6. 鸣牌 / 立直字符串（naki）

长度和关键字位置都是**硬校验**的，写错会直接报 `invalid naki string`。牌码部分用**两位数字**表示同一套牌码。

### 6.1 吃 `c` —— 长度 7，`c` 固定在 `[0]`

只能吃上家。

```
"c151416"  →  Chi { pai: 14(4m), consumed: [15(5m), 16(6m)] }
"c275226"  →  Chi { pai: 26(6p), consumed: [27(7p), 25(5p)] }
```
位置：`[1..3]` = 被吃的那张，`[3..5]`、`[5..7]` = 手上出的两张。

### 6.2 碰 `p` —— 长度 7，`p` 在 `[0]` / `[2]` / `[4]`

| `p` 位置 | 来源 | 被碰的牌 | 手上两张 |
| --- | --- | --- | --- |
| `[0]` | 上家 kamicha | `[1..3]` | `[3..5]`、`[5..7]` |
| `[2]` | 对家 toimen | `[3..5]` | `[0..2]`、`[5..7]` |
| `[4]` | 下家 shimocha | `[5..7]` | `[0..2]`、`[2..4]` |

```
"p191919"  →  碰 1p，来自上家    （ranked_game.json）
"47p4747"  →  碰 7z(中)，来自对家（ranked_game.json）
"3737p37"  →  碰 7s，来自下家
```

### 6.3 大明杠 `m` —— 长度 9，`m` 在 `[0]` / `[2]` / `[6]`

从 `takes` 中读取；`m` 两侧各 4 位共 4 张牌。

| `m` 位置 | 来源 | 被杠的牌 | 手上三张 |
| --- | --- | --- | --- |
| `[0]` | 上家 | `[1..3]` | `[3..5]`、`[5..7]`、`[7..9]` |
| `[2]` | 对家 | `[3..5]` | `[0..2]`、`[5..7]`、`[7..9]` |
| `[6]` | 下家 | `[7..9]` | `[0..2]`、`[2..4]`、`[4..6]` |

```
"m39393939"  →  杠 9s，来自上家
"26m262626"  →  杠 6p，来自对家
"131313m13"  →  杠 3m，来自下家
```

### 6.4 加杠 `k` —— 长度 9，`k` 在 `[0]` / `[2]` / `[4]`，写在 `discards` 里

| `k` 位置 | 之前碰自 | 加杠的牌 | 另外两张 |
| --- | --- | --- | --- |
| `[0]` | 上家 | `[1..3]` | `[3..5]`、`[5..7]`（`[7..9]` 为第 4 张） |
| `[2]` | 对家 | `[3..5]` | `[0..2]`、`[5..7]` |
| `[4]` | 下家 | `[5..7]` | `[0..2]`、`[2..4]` |

```
"3636k3636"  →  加杠 6s（chankan.json）
"4646k4646"  →  加杠 6z
```

### 6.5 暗杠 `a` —— 长度 9，`a` **只能**在 `[6]`，写在 `discards` 里

4 张同牌写成两两一组，第 4 张放在 `[7..9]`：

```
"424242a42"  →  Ankan { consumed: [42, 42, 42, 42] }   # 暗杠南
"2222a22"（非法）                          # a 不在 [6] → 报错
```

### 6.6 立直 `r` —— 长度 3，只能在 `discards` 里

```
"r21"  →  立直 + 手切 1p
"r60"  →  立直 + 摸切       （four_reach.json）
```

## 7. `results`（一局的结束声明）

`results` 是**无标签联合数组**，元素只能是：字符串（状态）、`[i32; 4]`（点数增减）、
或任意 JSON 数组（和了明细）。解析逻辑（`log.rs`）：

- `results[0] == "和了"` → 和了局；
- 否则 → **流局**，取 `results[1]` 作为四家点数增减（缺失则 `[0,0,0,0]`）。

### 7.1 和了局

```jsonc
[ "和了",
  [0, 0, -7700, 7700],                                  // 第 1 个和了者：四家点数增减
  [3, 2, 3, "30符4飜7700点", "役牌 發(1飜)", "混一色(2飜)", "赤ドラ(1飜)"],  // 和了明细
  [0, 0, 2000, -2000],                                  // 第 2 个和了者（双响/三响时才有）
  [2, 3, 2, "30符2飜2000点", "役牌 發(1飜)", "ドラ(1飜)"]
]
```

- 和了明细从 `results[1]` 开始**每两个元素一组**：`[点数增减, 和了明细]`。
- 明细数组里**只有前两个元素被读取**：`[0]` = 和了者（`who`），`[1]` = 放铳者（`target`，自摸时等于 `who`）。
  第 3 位起的符数/飜数/役名等文字**不参与**转换，可以随便写（`double_ron.json`、`suukantsu_1.json` 都有双响）。
- `ura_indicators`（下标 3）会被整组塞进每个 `Hora.ura_markers`。

### 7.2 流局 / 途中流局

```jsonc
[ "流局", [1500, 1500, -1500, -1500] ]     // 听牌料等
[ "九種九牌" ]                              // 无点数数组 → 全部按 0 处理
[ "四家立直" ]
```

`results[0]` 只要不是 `"和了"` 就按流局处理，所以 `九種九牌`、`四家立直`、`三家和了`
这类途中流局直接写状态字即可（测试牌谱 `kyushukyuhai.json` / `four_reach.json` 就是这样）。
只有 `"和了"` 是**魔法字符串**，不能写错。

## 8. 校验与常见报错

来自 `convlog` 的错误（`ConvertError` / `ParseError`）：

| 报错 | 触发原因 |
| --- | --- |
| `not four-player game` | `rule.disp` 含 `三` 或 `3-Player` |
| `invalid json` / serde 错误 | 顶层缺 `log` / `name` / `rule`；`name` 不是 4 个；`haipai_*` 不是 13 张；牌码非法 |
| `insufficient dora indicators` | 杠了但 `dora_indicators` 没有追加对应的指示牌 |
| `insufficient take sequence size` | 某家轮到摸牌，但 `takes` 已用尽 |
| `insufficient discard sequence size` | 某家有摸牌，但 `discards` 已用尽（忘写 `60` / `r` 很常见） |
| `tsumogiri should not exist in discard table` | `60` 出现在了 `takes` 里 |
| `invalid naki string` | 长度不对、关键字位置不对，或牌码非法 |
| `unexpected naki: ... expected tile X from Y` | 鸣牌声明的来源座位或牌，与上一张打出的牌对不上 |

### 8.1 需要小心的歧义：同牌连续打出

若 A 家连续两次打出**同一张牌**，而 B 家碰/吃的是其中一次，单看结构化数据无法判断是哪一次。
`conv.rs` 用**回溯**处理：先假设碰的是第一次打出，若后续事件流对不上就回退改试第二次
（`testdata/confusing_nakis_*.json` 就是这些用例）。

自行造谱时，**同牌连续打出 + 有人鸣牌**的组合最容易踩坑；建议改一张牌或保证时序清晰。

读法示例（0 号位）：配牌 13 张；`takes` 的第 1 项 `41` = 摸东，第 4 项 `"47p4747"` = 碰中

## 10. 与 mjai 事件的对应

转换后的整体形状（`tenhou_to_mjai`）：

```
StartGame { names, kyoku_first, aka_flag }
  StartKyoku { bakaze, kyoku, honba, kyotaku, oya, scores, dora_marker, tehais }
  Tsumo / Chi / Pon / Daiminkan / Kakan / Ankan
  Dora            # 杠后追加，指示牌取自 dora_indicators 的下一个
  Dahai
  Reach / ReachAccepted
  Hora / Ryukyoku
  EndKyoku
...
EndGame
```

若只想验证 `takes` / `discards` 是否合法，用 `-i log.json --mjai-out - --no-review` 直接看输出的
mjai 事件流，字段含义见 `convlog/src/mjai.rs`。

## 11. 数据来源：怎么拿到一份真实牌谱

- 天凤：`mjai-reviewer -t <log-id> --tenhou-out log.json --no-review` 会把原始 tenhou.net/6 JSON 原样存下来，
  在该文件基础上改一小段来构造自定义牌谱最省事；
- 在线版 <https://mjai.ekyu.moe> 走的是同一套结构；
- 雀魂牌谱需要先转换成 tenhou.net/6 事件流再按本文档组装，参见仓库 `mjsoul.adoc`。
