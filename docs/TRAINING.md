## 0. 目标与红线

**目标**：以服务端内置的启发式 `Bot`（teacher）为基模，训练一个**深度策略网络**作为玩家，
再通过**自对抗（对抗式数据 + 联赛自对弈）**持续进化；全流程在一台个人 PC 上可跑。

**规则口径（2026-09 追记）：训练用的就是服务端引擎的 M.League 默认预设。**
链路是 `SelfPlay.oneGame` → `Rules.defaults()`（字段缺省 `preset = "mleague"`，构造函数即
`applyPreset("mleague")`），**只有显式传 `--preset <name>` 才会换**；而 `python/` 侧
（`online.py` / `dagger.py` / `bc.py` / `awr.py` / `ppo.py`）**从不传 `--preset`**，
所以 raw 轨迹、compact 紧凑集、P0–P4 的全部 run 都是同一套口径。预设内容（`Rules.applyPreset`）：

- 赤 3、食断（`kuitan`）、里宝/杠宝/杠里宝、无古役、**常时一番缚**（`minHan = 1`）
- 役满**不加倍**；**无中途流局**（三家和了按**头跳**算）；无流局满贯
- **无击飞 / 无和了止 / 无西入**（南 4 局庄家轮庄即终局）、**一位必要点数 = 0**
- **食い替え禁止**、包牌（含四杠子；暗杠计入大三元/大四喜）
- 25000 配给 / 30000 返还、**马点 30 / 10 / −10 / −30 + 头名赏 20**、同点平分加点
- 切上满贯、无累计役满、连风雀头 2 符
- 立直：无 1000 点/残牌要求，但**海底不可立直**、立直后暗杠须保持面子构成

⚠ **训练目标也吃这套规则**：`rank_points` 由生产 `RoundScoring.settle` 用 `Rules.uma` 算出，
`rewards.py` 的 `rank_weight · 顺位点` **直接读 `summary.json` 的数字**（刻意不在 Python 里重写
uma/oka）—— 换句话说"顺位点"这一项本身就是 M.League 口径。
⚠ **两个已知缺口**：① 数据集里**没有记录规则**（`summary.json` / compact `meta.json` 都没有
`preset` 字段），"这份数据是哪套规则采的"目前只能靠"没人传过 `--preset`"这个默认事实推断；
② 网络只看得见 `obs`（与规则相关的只有 `hand_red`、宝牌/杠宝、余牌这类），**看不到 uma /
一位必要点数 / 食替设置** —— 所以线上房间**逐项改规则**（`tenhou` / `majsoul` / `custom`）时，
合法性仍由服务端强制，但"用 M.League 数据训出来的取舍"是否还合适，**没有据可依**
（真要换口径就得换数据分布重训）。

**四条红线**（前三条来自 `AGENTS.md` §6.5，第四条是本文档的评测纪律）：

1. **训练侧只实现 `ActionPolicy`**（拿不到 `Round`）—— 结构上不可能作弊。想读别家手牌都没有入口。
2. **不给服务端加第三方依赖**（Maven / ONNX / PyTorch）。最终形态是：Python 训练 → 导出权重 →
   **纯 Java 手写前向**（`java -jar` 自包含是硬约束）。
3. **训练期间 teacher 冻结**：改 teacher 的行为＝改训练标签＝**旧数据集全部作废**。
   teacher 只作为"基模 / 标注器 / 评测锚点"，不参与调参。
4. **评测先行**：没有配对评测与显著性口径之前，任何"变强了"的说法都不成立（见 §7）。
5. **遵守 §0.1 的三条机器纪律**（数据只落 S 盘 / GPU ≤80% / CPU ≤75% 的核）——
   它们是**使用者的硬约束**，不是性能建议：越界就停，宁可少跑几代。

### 0.1.1 数据根与配额（约束 ①）

```
S:\mahjong-training\
├─ raw\        采集下来的 jsonl 原样（最大的一坨）
├─ compact\    jsonl 转出的紧凑数组（训练直接读它）
├─ ckpt\       检查点（最新 N 个 + 历史最好）
├─ league\     联赛种群（每代一个 checkpoint）
├─ logs\       训练/评测日志与 summary
└─ probe\      冒烟测试的小样本（用完即删）
```

- **实测体积**：`--selfplay 48 --workers 24` → **53.5 MB / 48 场 = 1.12 MB/场**（703 决策/场、1.59 KB/决策）。
- **迁移记录（2026-09）**：数据根从 `T:\mahjong-training\`（TrainingData，约 58 GB）搬到
  `S:\mahjong-training\`（Silicon_files，**221 GB 可用**）。**为什么**：T 盘的**每文件开销**是采集吞吐的
  天花板 —— 把每场轨迹从 1.1 MB 压到 21 KB（`--sample 64`）吞吐**完全不变**（0.63～0.77 场/秒），
  且 java 只占 ~15/24 核（9 个 worker 卡在文件写入上）；顺序大块写在 T 盘能跑 50.7 MB/s，
  所以瓶颈不是带宽。**怎么搬的**：`robocopy /E /COPY:DAT /MT:16` → 逐目录核对文件数与字节数
  （raw 6430/1318.2 MB、compact 88/7374.3 MB、ckpt 15/7.7 MB、probe 50/54.5 MB，**四项全等**）
  → 抽样 SHA256 比对（权重 `net.bin`、`meta.json`、轨迹 `g0.jsonl`、sidecar `g0.feat.bin` 全一致）
  → 在 S 盘上跑通「写探针 → 采集 12 场 → `selfplay-check` DATASET PASS」。T 盘原位只留一张
  `MOVED-TO-S.txt`。迁移后的吞吐对照见 §1。
- **配额闸门（写之前先查剩余，超了滚动淘汰最旧的，raw 先淘汰）** —— 三道，依次判：
  ① 分项：`raw ≤ 80 GB`、**`compact ≤ 116 GB`**、`ckpt ≤ 2 GB`、`league ≤ 1 GB`、`logs ≤ 1 GB`；
  ② **数据根总配额 ≤ 200 GB**（`paths.TOTAL_QUOTA_GB`，2026-09-26 用户指定「S 盘上限 200 GB」时新增；
  它只在 `raw` / `compact` 里淘汰 —— 这两类是"每代一份、可复算"的）；
  ③ **任何时刻保留 ≥ 10 GB 余量**（`MIN_FREE_GB`，jsonl 写满盘会让采集静默失败）。
  ⚠ **分项之和 = 总配额 = 200 GB**（80+116+2+1+1）：分项加起来够不到总量时，"总配额"就是一句空话。
  ⚠ **`compact` 10 → 50 → 100 → 116 GB**（2026-09，用户多次上调）：P4 的世代循环每代一份紧凑集（~1.5 GB），
  四代就把 10 GB 顶爆，滚动淘汰**按 mtime 从最旧的开始删**、不区分"废弃数据集"与"还要复算的数据集"，
  于是把 `compact/rl-001`（P3 的数据集）删了。116 GB ≈ 77 代的余量（`raw` 80 GB ≈ 44 代）。
  ⚠ **`enforce_quota` 是在 `allocate()` 时检查的**，而目录是之后才长大的（`dataset build` 要几分钟），
  所以**实际占用会超出配额一代的量**——看 `paths.report()` 时别把那当成 bug。
  ⚠ 盘的**物理容量**仍是最终闸门（`MIN_FREE_GB`）：配额放大不等于可以无限堆 —— S 盘 231 GB（`free` 才是真相，
  200 GB 是**策略上限**，不是"一定有 200 GB 可用"）。
- ⚠ **仓库里不留训练数据**：`server\build\` 下的探针目录只在冒烟时用、**用完即删**；
  要长期留的小样本（≤ 50 MB）也放 `S:\mahjong-training\probe\`。
- ⚠ **落盘失败是"静默降级"**：`SelfPlay` 建不出目录时只打一条
  `WARN 轨迹目录创建失败，改为不落盘` 就继续跑 —— 采集"看起来成功了"却一个文件都没有。
  所以：**采集前先验证数据盘可写**（写个探针文件再删，`paths.ensure_root()` 就是干这个的），
  **采集后立刻看文件数**并跑 `node tools\selfplay-check.mjs <dir>`。
- ⚠ **沙箱/权限（本环境实测）**：在受限工作区策略下（DSH `workspace-write`），Java/Python **子进程**写
  `S:\` 会被直接拒绝（`java.nio.file.AccessDeniedException` → 上面那条 WARN）。
  此时必须在**放宽权限的会话**里跑，或由使用者在本机直接跑；
  ⛔ **不要**改成写仓库目录来"绕开"（那就是违反约束 ①）。

### 0.1.2 CPU 预算：≤ 24 / 32 核（约束 ③）

| 环节 | 设置 | 为什么 |
| --- | --- | --- |
| Java 自对弈采集 | `--selfplay … --workers 24` | ⚠ **必须显式传**：默认值 = `availableProcessors()` = **32** → 一跑就越界 |
| 兜底（改不动命令行时） | `-XX:ActiveProcessorCount=24` | 用 JVM 参数给任何 Java 进程封顶 |
| Python 训练 | `torch.set_num_threads(4)` + `OMP_NUM_THREADS=4`、`MKL_NUM_THREADS=4`、DataLoader `num_workers=4` | torch 默认会吃满所有核 |
| 并行纪律 | **生成与训练不要同时跑** | 24 + 4 = 28 > 24 会越界；确要并行就按"总活跃线程 ≤ 24"重分（例：生成 16 + 训练 8） |

- **约束下的实测吞吐**：`--workers 24` → **1.42～1.44 场/秒**（2026-09 迁盘后实测：写 `S:` 1.42、
  不落盘 1.44）→ **≈ 5.1k 场/小时 ≈ 3.6M 决策/小时 ≈ 7.8 GB/小时（`--sample 1`）**。
  ⚠ 更早的记录（1.95～2.40 场/秒）是**另一个代码版本**下的值，别混用（见 §1 表）。
- 观测：`Get-Counter '\Processor(_Total)\% Processor Time'`（32 核上 75% ≈ 24 核满载）。

### 0.1.3 GPU 预算：≤ 80%（约束 ②）

- **判据口径 = 时间平均**（实测结论）：`utilization.gpu` 是**瞬时**值、抖动极大 ——
  同一段小网络训练里 **均值 36% / 瞬时峰值 98%**。所以"≤80%"只能按窗口均值守，
  瞬时尖峰无法用软件保证（要硬压只能限功率 `nvidia-smi -pl`，那是设备级设置，动它要慎重）。
- **机制 = 占空比节流**（**已实测有效**）：常驻一个 `nvidia-smi ... -l 1` 子进程采利用率
  （⚠ 别每步 fork 一个：spawn 一次几百毫秒、比训练一步还贵，而且只会拿到尖峰），
  控制环看**最近 3 秒的均值**、自适应插 sleep。
  实测：稳态均值 **46%（≤80% ✓）**，代价是吞吐 470 → **371 步/秒**（约 21%）。
  ⛔ **不要**用 `nvidia-smi -lgc` 锁频 —— 那是**全局设置**，会影响机器上其它程序。
- **显存**：`torch.cuda.set_per_process_memory_fraction(0.8)` 是"相对整卡"的比例，但
  **本机空闲时就已有 ~1.1 GB 被别的进程占用**（实测 `总 7.93 GB / 已占 1.14 GB`）→
  训练进程把 batch 定在"**自己 ≤ 4.5 GB**"以内（实测 0.57M 参数 / batch 4096 只用 **0.07 GB**）；
  更稳的做法是用 `torch.cuda.mem_get_info()` 动态选 batch。
- 观测：`nvidia-smi --query-gpu=utilization.gpu,memory.used --format=csv -l 5`。
- **这些已经写成代码并自检**：`python/verify_env.py`（见 §1 末）逐项验证上面的机制，
  里面就有一段**节流验证**（带节流跑 10 秒，判据"最近 3 秒均值 ≤80%"）。
  `python/mahjong_ml/paths.py`（数据根 + 配额闸门）与 `guard.py`（线程封顶 + 采样节流 + 越界即停）
  是**第一批要写的模块**，可以直接复用 `verify_env.py` 里的 `GpuMonitor` / `DutyCycle`。
  P0 的验收里含一条"越界自检"（见 §4）。本机探针数据留在 `S:\mahjong-training\probe\`。

## 1. 实测算力预算（本机 · 2026-09）

一次 `--selfplay` 探针（`--hands` 未限、完整半庄）。**参考值**（未受限的 32 workers）：

```powershell
java '-Dstdout.encoding=UTF-8' -jar server\build\mahjong-server.jar `
     --selfplay 64 --workers 32 --rotate --seed 1 --out server\build\sp-probe
# == 自对弈汇总：64 场 / 745 小局 / 703 决策/场，用时 29.3s（2.18 场/秒，1536 决策/秒），workers=32
#    流局率 11.0%   平均每场 11.6 小局
```

**§0.1 约束下的实际跑法**（`--workers 24` + 数据落 S 盘）——**以后一律用这条**：

```powershell
java '-Dstdout.encoding=UTF-8' -jar server\build\mahjong-server.jar `
     --selfplay 48 --workers 24 --rotate --seed 2 --out S:\mahjong-training\raw\seed2
# == 自对弈汇总：48 场 / 561 小局 / 720 决策/场，用时 24.6s（1.95 场/秒，1407 决策/秒），workers=24
#    落盘 49 个文件 / 53.5 MB
```

| --- | --- |
| 机器 | 32 逻辑核 / 工作区盘 `C:` 空闲 **92.5 GB** / **数据盘 `S:`（Silicon_files）空闲 221 GB** / **RTX 5060 Laptop 8 GB**（Blackwell sm_120，空闲时已占 1734 MiB）/ Python 3.12.13（`.venv`，仅 numpy+torch）+ uv 0.11.7 |
| 对局吞吐（**训练端 C++ 生产者**，2026-09，`MAHJONG_PRODUCER=cpp`） | **≈Java 的 35–95×**（逐字节等价，见 `docs/TRAINER-CPP.md` §6.14/§6.16/§6.17）：4 策略混桌（`net:gNN,teacher,first,random --rotate`，24 workers）**78–83 场/秒**（1200 场 14.5–15.4 s）；**P5 世代采集**（2 席 `net:<上一代>#1.0` + `teacher,random`，16 workers）**49.6 场/秒**（2000 场 **40.3 s** / 151.9 万决策 / 37,707 决策/秒）；纯 `teacher×4`（24 workers）**≈135 场/秒**；2+2 配对（800 场）**≈57 场/秒** |
| 对局吞吐（**迁盘后实测，2026-09**） | **1.44 场/秒**＝不落盘的纯算力上限；**写数据盘 S: 1.42 场/秒**（全量轨迹 429.6 MB/400 场）；**写工作区 C: 1.23 场/秒** —— 见下面第 1 条（**Java 生产者**口径） |
| 对局吞吐（早先记录，**条件不同**） | 2.18 场/秒（`--workers 32`）/ 1.95～2.40 场/秒（`--workers 24`）—— ⚠ 与上面同条件却对不上，中途服务端有改动（配牌/回放/训练接口），**要比较必须同版本同条件**，别跨版本引数 |
| 对局吞吐（**历史：写 `T:` 的实测值**） | **1.41 场/秒**（800 场连跑、`--sample 2`→ 435 MB / 9.5 分钟）；`--sample 64` 时 0.63～0.77 场/秒 —— 迁盘前的瓶颈，见 §0.1.1 |
| 轨迹体积 | 703 决策/场、**1.59 KB/决策** → **1.12 MB/场**（48 场实测 53.5 MB）→ `--sample 1` 约 **7.8 GB/小时**（写本机盘） |
| 顺位方差 | 256 个座位-场：placement 均值 2.5、**σ = 1.118** |

**三条派生结论**：

1. ✅ **迁到 S 盘后，"写盘"这件事基本不花钱了**（迁盘后实测，同一版代码/同样 24 workers/全量轨迹）：
   **不落盘 1.44 场/秒 → 写 S 盘 1.42 场/秒**（≈1%，噪声内）；反倒**写工作区盘 C: 只有 1.23 场/秒**（−15%）。
   对照**历史值**（迁盘前）：写 `T:` 1.41、写工作区 2.40 —— 也就是当年掉的那四成**是 T 盘的问题**，
   不是"每场一个文件"的固有代价。T 盘的毛病在删除上也能看出来：**删 6,123 个文件花了 35 分钟**
   （≈3 文件/秒）。
   → **采集一律 `--out S:\mahjong-training\raw\…`**；别写工作区盘，也别再往 T 盘写。

## 2. 架构决策：两种接法，什么时候用哪个

`PROTOCOL.md` §8 定义了两种接法，本方案**两条都用**，按阶段切换：

| | **A. 外部进程当玩家** | **B. 进程内策略注入** |
| --- | --- | --- |
| 信息集 | 既有下行报文（结构上不可能作弊） | `mahjong.ai.Observation` 白名单 |
| Java 改动 | **零** | `Policies.byName` 加 `net:<权重文件>` + 纯 Java 前向 + 特征抽取 |
| 自对弈速度 | 受 TCP/思考时限约束，慢 | 与 teacher 同速（2.18 场/秒） |
| 配对评测 | 需要自己实现（同 seed 不易保证） | `--selfplay --rotate` 直接给配对数据 |
| 现成通道 | `create_room {fill_bots:3}` + `ready` → **一个 Python 进程立刻能和 3 个 teacher 打完一场** | `--policy net:a,teacher,net:a,teacher` |
| 适合 | 研究期（P1/P2 起步、换架构随便试） | 生产推理 + 大批量自对弈（P3 之后必须） |

**路线**：P1/P2 用 A（零改动、当天出基线）→ **P3 之前落地 B**（否则 RL 的样本吞吐不够）。

**B 形态要落的 Java 改动清单**（每项都要配 `SelfTest` 断言）：

| 改动 | 位置 | 断言 |
| --- | --- | --- |
| ✅ 纯 Java 前向（权重加载 + trunk + 打分头） | `ai/NeuralPolicy.java`（**已落地**） | `SelfTest.neuralForwardTests`：与 Python 的 golden 输出**逐元素**对拍（状态/候选 <1e-4、logits <1e-4、argmax 一致）+ 红证（输出偏置 +1 → 每条 logit 恰好 +1） |
| ✅ **特征抽取**（obs → 输入向量，与 Python 同一规格） | `ai/Features.java`（基础 544/88）+ `ai/ObsFeatures.java`（派生 71/8；v3 起） | 同上的 golden 夹具（含 `hand`/`visible` 是 `int[]` 还是 `List` 这类"两条通路不同形态"的坑） |
| ✅ `--policy net:<权重文件>` | `ai/Policies.java` 的 `byName` | 构造期校验魔数/格式/**特征维度**；运行期仍过 `fromAction` 三道保护 |
| ✅ DAgger 标注字段（`teacher` / `teacher_index`） | `train/TraceRecorder.java` + `SelfPlay --teacher-label` | `PROTOCOL.md` §8.4 已写；`selfplay-check.mjs` 字段白名单与合法性校验同步（2026-09） |
| ✅ 顺位点统计（马点+头名赏） | `train/SelfPlay.java` | 与 `RoundScoring.settle` 对拍 |

⚠ **回退纪律**：任何一种"加载失败 / 维度不符 / 动作非法"都必须退回内置 teacher
（`Policies.fromAction` 已有三道保护；`net` 的加载失败要发生在**构造期**并把原因打到日志）。

## 3. 模型与特征设计

### 3.1 动作建模：候选打分（不是固定 79 路 softmax）

一次询问里的合法动作由服务端给全（`Observation.legal`），所以：

```
trunk(obs)                 →  h ∈ R^d
score(h, candidate_emb)    →  每个合法动作一个标量   →  softmax over legal（+ 掩码）
```

理由：`chi` / `kan` 是**参数化**的（一次询问里最多各几种），
`PROTOCOL.md` §8.3 的固定头 79 槽只覆盖打牌/立直/无参动作；候选打分天然统一处理全部动作，
并且**逐条对齐轨迹里的 `chosen_index`**（"枚举 + 掩码"的监督信号）。
候选特征至少含：动作类型 one-hot、牌码（若参数化）、该动作之后的向听/进张/危险度、
`tsumogiri` 声明位、（吃/碰/杠）鸣后向听与是否有役计划。

> 兼容做法：打牌/立直仍可走固定 37 槽（打牌 37 + 立直 37）作为辅助头，便于与 teacher 的动作直接对齐。

### 3.2 输入特征（**封闭集合**，只许含合法信息）

| 组 | 内容 |
| --- | --- |
| 自家手牌 | 34 维计数（或 4 层 one-hot）、赤五标记、`drawn`（刚摸到的牌） |
| 副露 | 四家 × 各副露（kind + 牌 + from + 赤），建议编码成 4×34 的"明牌计数"+ 类型通道 |
| 牌河 | 四家 × 34 计数 **+ 巡目分层**（早期/立直后/摸切 vs 手切，后两者对读牌极有用） |
| 公开状态 | `riichi`/`ippatsu`、`dora_indicators`、`scores`、`round{bakaze,kyoku,honba,dealer,riichi_sticks}`、`tiles_left`/`dead_wall_left`、`total_discards`、`kan_count`、`any_call`、`haitei`/`houtei`/`rinshan` |
| **位置与点数**（v3 落地） | 自己点数、与三家均值之差、**顺位**、与上一名/下一名的分差（`points/5`）。⚠ 四家块（副露/牌河/立直/一发/点数）一律**旋转到自己为下标 0** —— 不旋转时输入里没有"哪一格是我"的锚，实测只有 15.5% 的决策能靠账目恒等式反推出来（开局 90.7% 完全不可分，见 `NOTES.md` §6.5） |
| 询问上下文 | `kind`（turn / claim）、`from` / `called_tile`、`win_note`（`furiten`/`no_yaku`）、`legal` 掩码 |
| **派生特征**（**已落地** = 特征 v2 / v3） | `mahjong/ai/ObsFeatures.java`：逐张危险度 `danger_worst[34]` + `danger_riichi[34]`（68 维）+ v3 的 `[shanten_now, value_han, value_points]`（3 维，**打点粗估与 teacher 的押し引き同一把尺子** `HandEval.estimatedHan`）→ 共 71 维进**状态**；逐候选 `[shanten, advance_types, advance_tiles, wait_types, wait_tiles, good_wait_types, good_wait_tiles, dora_count]`（8 维 → 进**候选**）。**由 Java 算、Python 只读**（`--features` 写 sidecar，逐决策段 int16），两侧靠 `SelfTest.obsFeaturesTests` 的 golden 对拍钉住（obs 通路 == Round 通路，带红证） |
| （可选，未做） | teacher 在同一 obs 上的**动作 one-hot**、四家逐张危险度的**理由码**（`genbutsu`/`suji`/…）、鸣后"有没有役计划" |

**为什么必须带派生特征**：这些正是 teacher 自己吃的东西。把它们显式喂进去，
等于让网络"从 teacher 的视角起步"，收敛速度快一个量级；也顺带成为 P5b 混合策略的接口。

**teacher 动作 one-hot 入特征**是"以 teacher 为基模"的最直接落地：
网络只需学**增量**（`logits = f(obs) + α · teacher_onehot`），最坏情况退化成 teacher，不会比基模差。

### 3.3 规模与吞吐建议

| 项 | 建议 | 理由 |
| --- | --- | --- |
| 参数量 | **0.3～3M** | 显存预算"自己 ≤ 4.5 GB"（§0.1.3，卡上已有 ~1.7 GB 被占）+ 纯 Java 前向跑得动（见下面的实测：**一次决策的瓶颈是特征工程，不是网络**） |
| 结构 | MLP / 小 ResNet（1D conv 沿 34 维），d=128～512 | 34 维计数 + 少量通道，不需要大 Transformer |
| 混合精度 | bf16 训练，导出 float32（或 int8 量化） | 显存余量与 Java 侧速度；batch 用 `mem_get_info()` 动态定，别写死 4096 |
| 归一化 | 点数 `/1000`、巡目 `/18`、余牌 `/70`、计数 `/4` | 与 Java 侧**逐字一致**（见下） |

**推理开销实测（2026-09，本机 32 逻辑核 / JDK 21 / `bot-ai/ppo2-g04/net.bin`）**：
`nets.py` 里"Java 侧 < 100 µs/决策"那句只对**纯前向且候选很少**时成立 ——
真实一次决策的开销**几乎全在特征工程**（逐候选的进张/向听统计），不在网络。
（复现：`java -cp server\build\mahjong-server.jar tools\BenchForward.java <net.bin> <轨迹.jsonl>`；
⚠ 本机是笔记本，单线程跑分**三次抖动 ±30%**，下表给的是区间。）

| 环节 | 单线程实测 | 说明 |
| --- | --- | --- |
| `ObsFeatures.ofObs`（obs → 视图） | **3～4 µs** | 便宜 |
| `Features.state`（**v3：615 维 = 544 + 71 派生**） | **24～34 µs** | 含 68 维危险度 + 一次 `Shanten.min` + 打点粗估（v1/v2 是 607 维、12～15 µs） |
| **每个候选**的 `cand`（96 维 = 88 + 8 派生） | **0.5～0.8 ms** | `HandEval.of` 对 34 种进张各跑一次 `Shanten.min` —— 真正的开销 |
| trunk + 打分头（1 个候选） | **0.20～0.32 ms** | 266,753 参数、≈0.53 MFLOP |
| 每个额外候选（只多打分头） | **~85 µs**（JIT 热身后） | 45,313 MAC / 候选 |
| **整条 `logits`（一次决策，平均 9 个候选）** | **5～8 ms** | 网络只占 0.4～0.7 ms（**约 8%**），特征占九成 |
| 整条 `logits`（34 个候选，最坏） | 5～20 ms | 随动作类型变（`discard` 系最贵） |

- **模型侧**：0.27M 参数 / **1.02 MB fp32 权重**（`net.bin` = 1,067,040 B）/ 每次决策 1.3～3.5 MFLOP
  → **纯 CPU 绰绰有余，推理不需要 GPU**（GPU 只在批量训练时有意义）；权重常驻 L2、
  服务端仍是零第三方依赖。想再快，先优化 `HandEval`/`Shanten` 的逐候选统计（向量化 / 记忆化），
  而不是把网络改小。
- **v3 的一个实测取舍（为什么要写下来）**：状态段里**不放**"当前进张种数/枚数"。那要跑一次完整的
  `HandEval.of`（34 次 `Shanten.min`），实测 **≈0.94 ms/决策**（状态段从 ~26 µs 涨到 ~1 ms，40 倍）；
  而"打完这张之后"的进张本来就在**逐候选段**（`advance_types`/`advance_tiles`），决策时真正要比的是
  候选之间的大小 ⇒ 信息并不缺。最终状态段只加 `[shanten_now, value_han, value_points]`
  （一次 `Shanten.min` + 打点粗估，≈3 µs）。⚠ 以后再想"顺手把 X 塞进状态段"时，先按这张表量一遍。
- **端到端自对弈（`--selfplay`，不落盘，24 workers）**：`teacher×4` **2.28 场/秒**（1610 决策/秒）·
  纯网络 `x4` **1.73 场/秒**（1172 决策/秒）· 出厂默认的 `@2` 混合×4（网络 + 老师先验）
  **1.08 场/秒**（736 决策/秒）；单核 88（网络）～117（teacher）决策/秒。
- **线上牌桌**：机器人每步有 `Table.botDelayMs = 800 ms` 的**刻意停顿**（局间 10 s），
  一次决策只花 ~5 ms CPU ⇒ **算力不是瓶颈**（一张 4 机器人桌的 CPU 占用约单核的 2%；
  瓶颈在"每桌一个线程 + 刻意延迟"，不在推理）。复现方法：
  `--selfplay N --workers K --policy "net:bot-ai/ppo2-g04/net.bin,…"`（**不给 `--out` 就不落盘**，
  这时的场/秒才是纯 CPU 吞吐）。

### 3.4 特征契约（train / serve 一致性）——最容易静默出错的地方

- 规格**单一来源**：`python/mahjong_ml/features.py` 是权威；Java 侧是它的**移植**。
- **golden 对拍**：从真实对局导出 N（≥200）个 obs（覆盖 turn / claim / 立直 / 鸣牌 / 杠 / 流局边界），
  Python 与 Java 各算一遍特征，**逐元素比对**（写入 `python/tests/golden/`，双向各一条自检）。
  这条不过，训练出来的模型在 Java 里就是另一个东西。
- 归一化常数、字段顺序、缺省值（`drawn=null`、`from=-1`）都在 golden 里钉死。

### P3 · 离线强化学习（IQL / CQL）—— ✅ **已落地（2026-09），判据见下**
- **做法**：用自对弈数据 + 回填奖励学 `Q(s,a)` / `V(s)`（不需要在线采样），再用它改策略。
- **为什么选 IQL 而不是 CQL**：CQL 要在一批**没出现过的动作**上压 Q，而我们的动作空间是**每次询问
  现枚举的**（`legal` 里是 `chi:1m+2m` 这种参数化键）——"随机采一个动作"本身没有定义。
  IQL 只用数据里那个动作（expectile 回归 + 单动作 Bellman），与轨迹格式天然契合。

#### P3 的 MDP 口径（**判据全靠它**，实现见 `python/mahjong_ml/rewards.py`）

- **一条 episode = 某一家在一小局里的全部决策**（键 = `file` + `hand_no` + `seat`）。四家的决策
  在轨迹里是交错的，把"同一家的相邻决策"连起来才是单智能体视角。
- **奖励**：只有该家这一小局的**最后一个决策**吃 `hand_delta[seat]`（小局收支），其余 `r = 0`；
  **γ = 1**（小局收支不折现）→ 于是 **`V(s)` 的语义 = "本小局从这一手起还能再赚多少点"**，
  与 teacher 里那三个粗模型（`AVG_DEAL_POINTS` / `winProbability` / `dealProbability`）**同量纲**，
  所以"用价值头替换粗模型"这句话才有可比性。
- **每小局末尾 bootstrap 到 0**（不跨小局累计）——那是另一个量纲，要单独一轮，别混着说。
- **整场顺位点项（2026-09 第二轮，已落地）**：顺位点**本身就是"千点"量纲**（41,600 的 1 位 = 61.6，
  见 `DESIGN.md` 的精算例子），所以直接加：`reward = hand_delta[seat]/1000 + λ · rank_points[seat]`
  （`--rank-weight λ`；λ=1 时**名次成为主导项**，一手牌约 ±8 而顺位点约 ±60）。
  取值链路：紧凑集 meta 的**全路径**清单 → `g<N>.jsonl` 对回 run 目录的
  `summary.json` 的 `per_game[N].rank_points[seat]` —— **读 Java 算好的精算结果，不在 Python 重写
  uma/oka**（重写必然漂移）。⚠ 迁盘遗留：迁盘**前**建的紧凑集 meta 里还是旧根路径，
  `rewards._resolve_trace_path` 会按当前数据根**重映射**（找不到就报错，绝不悄悄当 0）。
- ⚠ **选择标准要跟用途走**：`--select-metric {val_mae,val_pearson,val_ep_pearson}`。
  只做校准就用 MAE；**给 AWR 当指南针必须用相关系数** —— 实测带顺位点项时，按 MAE 选中的 ep4
  小局级 ρ 只有 **+0.20**，而 ρ 最高的 ep40 是 **+0.55**（MAE 反倒差于恒 0）。
  道理：MAE 奖励"缩到均值附近"的保守模型，而 AWR 用 `Q−V` 的**排序**。
  附带发现：**顺位点目标给出的排序能力明显更强**（ρ 0.55 vs 只用小局收支的 0.40）。
- **数据**：`compact/rl-001` = `raw/{bc-001, dagger-01, control-r1}` 三源合并，训练 **622,472** 条决策 /
  **57,355** 条 episode（均长 10.85 步）；非零奖励占 **72.7%**（赢 27.0% / 输 45.7%）、
  学生行占 15.0%。为此紧凑集在 2026-09 新增了 `file` / `hand_no` / `seat` / `placement` / `is_student`
  五列（`dataset.RL_COLUMNS`；**旧数据集读回来是 None**，`rewards.py` 会明确报错让你重建，
  而不是拿 `game` 冒充 `file` —— 那个跨来源会撞车）。

#### 判据① 价值校准（IQL，`offline_rl.py`）

- 训练：`python -m mahjong_ml.offline_rl --data …/compact/rl-001 --label iql-001 --epochs 40 --lr 5e-4`
  （IQL：expectile τ=0.7 的 V + 单动作 Bellman 的 Q + Polyak 目标网络；CPU 线程与 GPU 占空比走 `guard`）。
- 校准口径：`V(s)` 对 **return-to-go**（= 该小局该家的收支，千点单位），另给**按小局聚合**的版本；
  **必须与两个同粒度基线比**：恒预测 0、恒预测常数（**用训练集均值**，否则基线自己吃了验证集信息）。
- 结果：**实测两轮**（同数据 `rl-001`、同超参、40 epoch）：

  | 轮次 | 奖励 | 选择标准 | 行级 MAE（基线 6.2408/3.0634） | 小局级 ρ | 有收支小局的 ρ |
  | --- | --- | --- | --- | --- | --- |
  | `iql-002` | 只有小局收支（λ=0） | val MAE | **3.0266** ✓（恒0 3.0634） | +0.396 | +0.418 |
  | `iql-003` | +整场顺位点（λ=1） | val MAE | **6.2157** ✓（恒0 6.2408） | +0.203 | +0.213 |
  | **`iql-004`** | +整场顺位点（λ=1） | **小局级 ρ** | 6.3991 ✗（打不过恒 0） | **+0.554** | **+0.577** |

  小局级 MAE 那一列：`iql-004` 是 6.2726（恒 0 基线 6.3247，**赢**）；行级 MAE 输是因为它的预测
  **有方差**（真的在区分局面），而一手牌的收支本身噪声极大。

  **裁定：判据① —— 按"排序"口径 ✅ 通过、按"逐行 MAE"口径 ❌ 不通过。**
  说清楚：价值头**能排出局面的好坏**（小局级 ρ = **+0.554**，有收支的小局 +0.577），
  **但不是逐点校准的**（行级 MAE 6.399 打不过"恒预测 0"的 6.241）。
  ⚠ 而且**两个口径会选出不同的模型**：MAE 选出 ep4（ρ 只有 +0.20）、ρ 选出 ep40（ρ +0.55）。
  道理是 MAE 奖励"缩到均值附近"的保守模型，而 AWR 用 `Q−V` 的**排序** ——
  所以 `--select-metric` 的默认值只适合"只做校准"的用途，**给 AWR 当指南针必须选相关系数**。
  附带结论：**顺位点目标显著提升排序能力**（ρ 0.554 vs 只用小局收支的 0.396）——
  名次比"这一小局赚多少点"好预测（后者被一把大牌或一次放铳主导）。
- ⚠ 另一条**必须记的教训**：验证指标在**中段之后会持续恶化**（λ=0：ep6 的 3.0266 → ep40 的 3.4709），
  所以第一版"存最后一个 epoch"等于交出最差的模型；现在按 `--select-metric` **回滚最优 epoch** 再落盘。
- 回归：`python/selfcheck.py` 里有**转移组装 / 奖励口径 / 校准指标**的断言（含"恒预测 0 不能号称
  赢过恒预测 0""完全反向预测 → 相关系数 −1"这类防自欺的用例）。

#### 判据② 策略改进（AWR，`awr.py`）

- `A(s,a) = Q(s,a) − V(s)`（冻结的 IQL critic）→ 权重 `w = clip(exp(β·A), 0, w_max)` →
  加权 BC `−Σw·log π(a|s)/Σw`，**外加行为锚定** `λ·CE(π, a)` 防漂移。
- ⚠ **必须报 ESS（有效样本量）**：β 太大时权重塌到少数样本上，"指标好看"也不可信。
- ⚠ **离线 top-1 不是判据**：AWR 优化的是小局收支，不是"更像老师"——强度只能看同牌山配对实战。
- **结果（两轮，同数据同评测协议）**：

  | 配对（同牌山、`--rotate`、`--sample 64`） | Δ 顺位点 | 95% CI | p | 胜/负/平 | sd(Δ) | 检出 Δ=2 需要 |

### P4 · 在线自对弈 RL（PPO / A2C）—— ✅ **已落地（2026-09），判据见下**

**三条保命措施（缺一不可）**：① BC/IQL 初始化；② 奖励塑形（不能只给终局）；③ 联赛对手（见 P5），
不要只跟自己最新版打。

#### 实现（三个模块 + 一个 Java 侧的探索口）

| 文件 | 干什么 |
| --- | --- |
| `python/mahjong_ml/ppo.py` | PPO 训练：行为策略重算 `π_old`、GAE、裁剪代理目标、独立价值头 `nets.ValueNet`、KL 早停 |
| `python/mahjong_ml/online.py` | **世代循环**（采集→导数特征→紧凑集→PPO→导出）与**联赛阶梯**（Elo + 2+2 配对） |
| `python/mahjong_ml/league.py` | 对手池：Plackett-Luce Elo（按场聚类 bootstrap）、"谁克我就多跟它打"的加权采样 |
| Java `net:<权重>[@<α>][#<T>]` | **温度采样**（探索口）。`T≤0`/省略 = argmax，与加这个语法之前**逐决策相同** |

- ⚠ **为什么 P4 非要 Java 侧改动**：PPO 是**同策略**算法，行为策略必须随机。`net:` 原来只会 argmax，
  采出来的数据全落在"贪心那一条"上 —— 重要性权重 `π_new/π_old` 没有支撑集（离线 RL 不受影响，
  它直接取数据里那个动作）。契约见 `PROTOCOL.md` §8.4，回归见 `SelfTest.samplingPolicyTests`。
- 随机源按 `(seat, gameSeed)` 派生、**每局新建**（`Policies.mixSeed`）：并行度与局序都不影响
  同 seed 的轨迹，`AGENTS.md` §6.5 的"同种子可复现"照旧成立。

#### 口径（**与 `rewards.py` 完全相同，不许另立一份**）

- episode = 某一家在一小局里的全部决策；γ = 1；奖励只记在小局末决策（`hand_delta`），
  整场末决策再另加 `rank_weight · 顺位点`。
- **λ = 1**（不是 PPO 论文惯用的 0.95）：奖励是"末决策单点"，λ<1 会让前几步的优势按**剩余步数**
  衰减 —— 那是系统性偏差。λ=1 时 GAE 恰好塌成 `A = R − V`，`python/selfcheck.py` 钉着这条等价性。
- **行为策略 = `softmax(z_θ/T)`**，所以训练的策略就是同一个 T 下的 `π_θ`；部署仍取 argmax，
  而 argmax 对 T 不变 ⇒ **温度只影响探索，不影响上线动作**。⚠ `--temp` 必须与采集时 `#<T>` 一致。
- **策略损失只算"学生行"**（`is_student == 1`），对手座位（teacher/脚本）的行**仍进价值损失**。
- 价值头**不导出到 Java**：线上依旧只认 `CandidateScorer`，`NeuralPolicy.java` 的权重格式一行没动。

#### 怎么跑

```bash
cd python
python -m mahjong_ml.online run --init S:\mahjong-training\ckpt\awr-002\model.pt \
       --init-value S:\mahjong-training\ckpt\iql-004\model.pt \
       --label ppo --generations 4 --gen-games 1500 --temp 1.0 --epochs 4 --workers 20
python -m mahjong_ml.online ladder --label ppo --generations 4 --games 1200 --pair-games 800
# 调步长之前**先量策略位移**（30 秒）：各代网络在固定数据集上的贪心一致率
python -m mahjong_ml.online displace --label ppo --generations 4 --data <某一代的紧凑集>
```

- 每代采集 = **2 席自己 + 2 席联赛对手**（`--rotate` 轮座位）；第一代先跟 `teacher` 打，
  之后对手按 `league.select_weights` 采（老师**常驻一席**，它是"没有变弱"的基准）。
- 价值头冷启动用 P3 的 IQL critic（只取 `trunk.* + v_head.*`）：从零开始时前几代的优势
  基本等于"回报减一个常数"，策略梯度方差极大。

**`--temp` 不是照抄的常数**（与 P5b 选 α 同一条纪律）：用
`python -m mahjong_ml.ppo --data <紧凑集> --init <权重> --explore-only` 量"温度 → 偏离贪心比例"。
实测 `awr-002` 在 `rl-001` val（40,000 条）：

| T | 平均熵 | 贪心那条的平均概率 | **采样偏离贪心** |
| --- | --- | --- | --- |
| 0.25 | 0.068 | 0.972 | 2.7% |
| 0.5 | 0.139 | 0.944 | 5.5% |
| **1.0** | 0.279 | 0.890 | **11.3%** |
| 2.0 | 0.503 | 0.801 | 20.0% |
| 4.0 | 0.761 | 0.687 | 31.0% |

⇒ 本轮取 **T=1.0（≈11% 的决策在探索）**：>30% 梯度噪声太大、<5% 几乎退回贪心。
⚠ `SelfTest.samplingPolicyTests` 里那条曲线是 **golden 夹具**（未训练的小网，logit 几乎相等）
的属性（"T=1 偏离 97%"）—— 它验的是**实现**，**不能**拿来选 T。

#### 判据（"过/不过"）

- **主判据**：Elo（Plackett-Luce θ）相对 `teacher` **单调上升**，且 `θ_i − θ_teacher` 的 CI 最终排除 0；
- **不许退化的旁证**：对脚本基线（`first`/`random`，阶梯 run 里同场出现）的 θ **不掉**；
  "对 teacher 变强、对 random 变弱" = 过拟合到自己的策略 ⇒ **回退**；
- **配对口径**：每代另跑 **2+2**（`net×2 vs teacher×2`）给顺位点的逐场配对 CI ——
  阶梯 run 是一席对一席，实测 `sd(Δ)≈80`（2+2 约 53），同样场次精度差一倍，**主判据不在那里读**。
  ⚠ **2+2 要跑两种座位配置**（2026-09-26 起，`online._arrangement_specs`）：`A,A,B,B` 与 `A,B,A,B`。
  轮转 `src=(seat+game)%4` **保持策略表的块结构** ⇒ 前者只采样"两席相邻"、后者只采样"两席对家"；
  单跑一组会把另一种座位关系留成未采样偏差（实测 v3 的 g05：相邻 +1.10 不显著，对家 +4.23 p=0.044，
  合计 n=1600 才 +2.66 [+0.14,+5.18]）。两组的 seed 基不同（独立样本），最后合成一个总 Δ。

#### 顺手拿到的判据①：**在线**价值头比 P3 的离线 critic 校准得更好

P4 的价值头与 P3 用的是**同一把尺子**（`ppo.value_report` = 逐点 MAE + 逐点 ρ + 小局级 ρ），
所以可以直接比。⚠ 严格说**不是受控对比**（评测切分不同：这里每代用当轮自对弈的 val，
P3 用的是 `rl-001` 的 val），所以只能说"**在线训练的价值头在这份更贴近自己策略分布的数据上，三项全过**"：

| 价值头 | 逐点 MAE vs 常数基线 | 逐点 ρ | 小局级 ρ |
| --- | --- | --- | --- |
| P3 `iql-004`（离线，λ=1，`rl-001` val） | 6.399 **> 6.241（不过）** | — | +0.554 |
| P4 `ppo-g01`（在线，第一代 val） | **5.750 < 6.010 ✓** | +0.599 | +0.663 |
| P4 `ppo-g02`（在线，第二代 val） | **5.541 < 6.359 ✓** | +0.688 | +0.737 |
| P4 `ppo-g03`（在线，第三代 val） | **5.572 < 6.401 ✓** | +0.699 | +0.743 |
| P4 `ppo-g04`（在线，第四代 val） | **5.403 < 6.486 ✓** | **+0.723** | **+0.765** |

读法：P3 那个 critic 的病灶是**逐点尺度**（排序好、绝对量偏乐观），而 P4 的价值头用
**同策略**新采的数据 + 冷启动自 IQL，把三项一起推上去了 —— **四代单调变好**（逐点 ρ 0.599 → 0.723、
小局级 ρ 0.663 → 0.765）；`V_old std` 从接近 0 涨到 6.8 → 12.8，说明它真的在预测而不是缩在均值附近。

### P5b · 混合 / 蒸馏 —— ✅ **混合已落地（2026-09）**
- **做法**：`logits = student(obs) + α · teacher_prior`（先验 = 老师在同一信息集的动作）。
- **已落地**：策略串 `net:<权重文件>@<α>`（`PROTOCOL.md` §8.4），α 缺省 0 = 纯网络（与旧行为逐决策相同）；
  实现是 **`Policy` 级组合**（`Policies.hybrid`，与 `TEACHER` 同级）—— 先验要调 `Bot.decide(Round, …)`，
  而 `ActionPolicy` 是故意拿不到 `Round` 的（反作弊口径），网络本身仍只看 `Observation`。
- **判据①（可证）**：α 极大 ⇒ argmax 必是老师那条 ⇒ **`hybrid(@∞) ≡ teacher`**。
  `SelfTest.hybridPolicyTests` 在**整局决策序列 + 终局分数**上断言这一点，并配一条非空转对照
  （纯网在同一探针上与 teacher 差 323/333 处 —— 否则"两边都等于 teacher"什么也证明不了）。
- **判据②（α 怎么选）**：α 与**训练过的网**的 logit 尺度绑定，**别照抄常数**——
  同一套代码在**未训练**的 golden 小网上 α=0.25 就 100% 让位。用
  `python -m mahjong_ml.hybrid` 量"让位曲线"：`margin` = (除老师那条外的最大 logit) − 老师那条的 logit，
  `margin < α` ⇔ 该行被老师接管。**bc-003 在 `dagger-r1[val]`（n=16,092）上**：
  margin 中位 **−4.08** / p90 **0.63**；让位 α=0.25 → **87.8%**、α=1 → 91.7%、α=2 → 94.8%、
  α=4 → **97.7%**、α=32 → 100%（推荐 α=4 @ 让位 95%）。
  ⚠ 这条曲线**只说明"让位多少"，不说明"更强"**：数据集里的真值就是老师，让位即"对"。
- **判据③（强度）**：只能靠同牌山配对实战（`mahjong_ml.eval`）—— 见下表。
- **判据④：配对实战（2026-09 round 1）** —— 2400 场同牌山配对（`--rotate`、两臂各 2 席、
  `seed 777001`、`--sample 64`；**54 分 02 秒 ≈ 0.74 场/秒**；整批过 `selfplay-check` = DATASET PASS）：

  | 配对 | Δ 顺位点 | 95% CI | p | 胜/负/平 | sd(Δ) | 检出 Δ=2 需要 |
  | --- | --- | --- | --- | --- | --- | --- |
  | **`hybrid@1` − 纯网**（2400 场） | **+1.95** | **[−0.21, +4.10]** | 0.045 | 1248 / 1149 / 3 | 53.11 | ~5535 场 |
  | **`hybrid@1` − `teacher`**（1200 场） | +1.20 | [−1.76, +4.12] | **0.977** | 600 / 598 / 2 | 52.31 | ~5370 场 |
  | （参照）纯网 − `teacher`（300 场，更早一轮） | −1.61 | [−7.65, +4.50] | 0.817 | 147 / 152 / 1 | 54.53 | ~5835 场 |

  同场汇总（臂 A：2400 场 = 每臂 4800 席场）：`hybrid@1` 平均顺位 **2.479** / 顺位点 **+0.97** /
  和了 22.5% / 放铳 16.1%；纯网 **2.521** / **−0.97** / 22.4% / 16.4%。
  （臂 B：`hybrid@1` 2.482 / **+0.60** vs `teacher` 2.518 / **−0.60**，和了 22.4%/22.6%、
  放铳 16.7%/16.0% —— 胜/负 600:598，**完全打平**。）

- **裁定（round 1）**：三条比较的**点估计都在 ±2 顺位点内、CI 全部跨 0** —— 用现有样本
  **分不出** hybrid / 纯网 / teacher 三者的强弱。唯一像信号的是对纯网的 **+1.95（p=0.045）**，
  但它正好卡在 0.05 上、且 `eval.py` 自己算出的"检出 Δ=2 约需 5535 场（80% 功效）"说明我们**就在分辨率边缘**；
  对 teacher 干脆是完全打平（p=0.977，胜 600 负 598）。
  → 可下的结论只有两条：① **混合机制正确且可证安全**（上位集合性质 + 2400 场零非法动作 + 整批
  DATASET PASS）；② **它的强度效应尚未确立**（要钉住 +2 还需再跑 ~5500 场，合并 n≈5100 把 CI 压到 ±1.5）。
  ⚠ 而且从机制上就能预判：α=1 时 **91.7% 的决策本来就听老师**，所以这一臂的天花板是"老师"，
  它测的是"学生那 5.7% 的自主决策是不是亏"，**不是**"混合产生了新能力"。
- **去向**：① 不再在"推理期把老师请回来"上继续调 α（天花板 = 老师，而天花板已经够到了）；
  ② 把混合**留作未来在线 RL 的保底**（α 取大 ⇒ 逐决策 ≡ teacher，可证不会更差）；
  ③ 真想超过老师只能靠**价值/胜负信号** → 回到 **P3（IQL/CQL）**；
  ④ "蒸馏"那一半（把"老师选了哪个候选"做成输入特征、让学生学会**选择性**听）留到 P3 之后再评估
  ——它是特征版本 +1 的改动，现在的证据不足以支持。
- **⚠ 与 DAgger 同一个陷阱**：学生状态分布的偏移本来就很小（基线在学生状态上只掉 0.003），
  所以"老师接管一部分决策"能换来多少强度，本身就该是**小效应**；要检出动它得几千场（见 §7）。
- **还没做的一半（蒸馏）**：把"老师选了哪个候选"做成**输入特征**再重训（让学生学会**选择性地**听老师）。
  那是特征规格改动（+1 维 → 特征版本 +1、golden 夹具重导），**先看混合实测有没有信号再决定**。

## 6. 自对抗进化的具体形式（对应 P5）

```
种群 = {teacher(冻结) } ∪ {net-v1 … net-vN} ∪ {first, pass, random}
每一代 g：
  ① 评估：当前 best 与池中每个对手打配对对局（rotate）→ 胜率矩阵 / Elo
  ② 采样对手：按 (1 − 对当前 best 的胜率)^p 加权（**打不赢的多打**）
  ③ 采集：best vs 加权对手的轨迹（含当前 best 自身的状态分布）
  ④ 训练：BC/DAgger 标注 + IQL/PPO 更新（保底项：对整个池子的最坏情况不能退化）
  ⑤ 入库：新 checkpoint 进池（保留历史版本，别覆盖）
```

**防退化三件套**：① 对手池只增不减（保留"曾经赢过我"的版本）；② 多样性下限（见 P5 判据）；
③ 对 teacher 与脚本基线的胜率作为**回归测试**，每次入库都跑。

## 7. 评测口径与显著性

`σ(placement) = 1.118`（实测）时，未配对、单侧 95%、CI 半宽 = Δ 所需的**每臂座位-场数**：

| 想检出的顺位差 Δ | 每臂座位-场 | 折算场次（4 座位相关，取保守） |
| --- | --- | --- |
| 0.05 | ≈ 3.8k | ≈ 1k～4k 场 |
| 0.10 | ≈ 960 | ≈ 240～960 场 |
| 0.20 | ≈ 240 | ≈ 60～240 场 |

- **配对阵（同 seed、`--rotate`）能把方差压下来**（同一副牌山比两个策略），是省算力的关键；
  显著性用 `per_game` 做**配对**检验（符号检验 / 自助法），不要拿总胜率硬比。
- **顺位点（rank_points）的尺子**（实测 `sd(Δ) ≈ 53`，来自 `net vs teacher` / `AWR vs BC` 的配对差）：
  95% 置信 + 80% 功效下，要检出 Δ 顺位点约需
  `n ≈ (2.8 × 53 / Δ)²` 场 —— **Δ=1.3 → ~13.7k 场、Δ=2 → ~5.5k 场、Δ=3 → ~2.5k 场、Δ=5 → ~0.9k 场**。
  ⚠ **口径更正的记录（2026-09）**：`eval.py` 的 `required_n` 第一版只用了 `z_{α/2}` —— 那其实是
  **50% 功效**（效应恰好压在临界值上、一半概率检不出），把所需场次**低估了 2.04 倍**
  （`(1.96+0.84)²/1.96²`）。现在默认 **80% 功效**（`power=` 可调），文档里所有"检出 Δ=2 需要 N 场"
  的数都按 80% 重算过（例如 sd=52.96 时 2695 → **5504**）；**实测的 Δ/CI/p 不受影响**，
  只有"还要打多少场"的推算变了。
  ⚠ 由此也别把"跑够 N 场就一定显著"当结论：N 只保证**真值等于 Δ** 时有 80% 概率检出；
  真值更小就要更多场（真值 1.3 而只有 5.5k 场时，检出概率约 53%）。
  ⚠ 所以"P4/P5 里的一次对比"动辄是**几千场**：按迁盘后的 **1.42 场/秒**（24 workers、写 `S:`）算，
  2.6k 场 ≈ **半小时**（迁盘前写 `T:` 时要一小时，见 §0.1.1）—— 那是 **Java 生产者**；
  **换 C++ 生产者（50–83 场/秒）后 2.6k 场 ≈ 半分钟**，所以"采样省盘"不再是速度手段，
  只剩省盘（以及 `eval.py` 的统计时间不变）。**做评测跑不需要全量轨迹** ——
  加 `--sample 64`（~11 行/场）只影响落盘行数、不影响 outcome 与 `summary.json`。
  ⚠ 但注意：**`--sample` 并不能提速**（实测 21 KB/场 与 1.1 MB/场 吞吐一样），
  提速的是**换盘**（`T:` 的每文件开销）—— 所以现在没必要为了速度去采样，采样只为省磁盘。
- **离线指标（对老师的一致率）也要按场聚类**：`python -m mahjong_ml.bc eval --data <紧凑集> --ckpt <模型>`
  给的是逐行口径；DAgger 那种"新旧模型比同一批学生状态"的场景走 `mahjong_ml.dagger.compare_on`，
  它用**按场聚类**的配对 bootstrap —— 一局里的决策高度相关，逐行 CI 会把 ±0.02 的事说成显著
  （红证在 `selfcheck.py`）。**离线一致率只说明"更像老师"，不说明"更强"。**
- **胜率 ≠ 顺位点**：本作是顺位制，评测报告必须同时给 **avg_place / 顺位点 / 1位率 / 放铳率**。
  P0 就是为这件事存在的。
- **报告纪律**：每个结论都带"场次 + 置信区间 + seed 基准"，否则不进结论。

## 8. 风险与对策

| 风险 | 表现 | 对策 |
| --- | --- | --- |
| **CPU 越界（>75% 的核）** | 机器卡顿 / 违反约束 ③ | `--workers 24` **显式传**（默认 32 会越界）、`torch.set_num_threads(4)`、**生成与训练不并行**（§0.1.2） |
| **GPU 越界（>80%）** | 违反约束 ② / 影响机器上别的程序 | 占空比节流（不锁频）；显存按"自己 ≤4.5 GB"定 batch（卡上已有 ~1.7 GB 被占）(§0.1.3) |
| **数据写到 S 盘之外 / 写满 S 盘** | 违反约束 ① / 采集中断 | 唯一数据根 `S:\mahjong-training\`；`paths.py` 配额闸门 + 滚动淘汰 + 留 ≥10 GB 余量（§0.1.1） |
| **S 盘写入被拒（沙箱）** | `SelfPlay` 只打一条 WARN，采集"成功"却零文件 | 采集前写探针文件验证；受限策略下必须在放宽权限的会话里跑；⛔ 不许改存仓库目录（§0.1.1） |
| **特征偏斜** | 训练指标好、Java 里表现差 | golden obs 双侧对拍（§3.4）；归一化常数单一来源 |
| **非法动作** | 服务端拒绝 / 退回 teacher | 只实现 `ActionPolicy` + 始终掩码 `legal`；`Policies.fromAction` 兜底 |
| **不可复现** | 同 seed 轨迹不同 | `PolicyFactory` 每局一实例；`debugDeterministicSeed`；策略不许跨局带状态 |
| **作弊模型** | 评测分数离谱 | 只用 `obs` 白名单；`selfplay-check.mjs` 当必过门；绝不喂 `Round.hand[other]` / 牌山 / 里宝 |
| **奖励稀疏 / 高方差** | Elo 乱跳、学不动 | 奖励塑形 + 配对评测 + 预先算样本量（§7）；先离线 RL 再在线 RL |
| **循环相克** | A 赢 B、B 赢 C、C 赢 A | 联赛 + 平均策略（NFSP 思路）+ 多样性下限 |
| **过拟合自己** | 对 random/first 反而变弱 | 回归测试（对基线的胜率不许掉） |
| **碰 teacher** | 旧数据集作废 | teacher 冻结；只改奖励与网络（红线 3） |
| **PyTorch 装不上 / 静默 CPU** | 训练极慢 | uv + Python 3.12 + cu128 轮子；装完**必须**验证 `torch.cuda.get_device_capability` |
| **磁盘爆** | 采集中断 | `--sample 4~8` + 紧凑格式 + 滚动窗口 ≤30 GB |
| **8 GB 显存** | OOM | ≤3M 参数、batch ≤4096、bf16、梯度检查点（必要时） |
