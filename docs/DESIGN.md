# 立直麻将 总体设计

## 目标

- **服务端**：Java 21，零第三方依赖（只用 JDK 标准库），可编译成单 jar 运行于 Ubuntu。唯一权威方：洗牌、配牌、摸切、鸣牌、和牌判定、役种/符数/点数、振听、流局、连庄、精算。
- **客户端**：Qt 6 Widgets + C++17，MinGW 构建，运行于 Windows。只负责：绘制牌桌、收集操作、播放事件反馈、与服务端通信。**不做任何规则判定**。

## 目录结构

```
mahjong/
├─ docs/          规则原文、协议契约、设计、部署
├─ server/        Java 服务端（build.sh 供 Ubuntu 使用）
├─ client/        Qt6 C++ 客户端（CMake）
└─ tools/         本地联调脚本（起服务端 + 机器人）
```

## 服务端分层

```
mahjong.util      Json（手写零依赖解析/序列化） / Log
mahjong.core      Tiles（牌编解码）/ Meld（副露）/ Rules（规则配置项与校验）/ Wall（牌山 + 王牌账）
mahjong.rules     Shanten(向听) Agari(和了形分解) Evaluator(役种 + 符 + 高点法)
                  Payments(点数授受) WinContext(和了上下文) YakuCodes(中文名 ↔ ASCII 码)
mahjong.game      Round(一局状态机) Table(房间/座位/线程)
                  ── 以下四个是从 Round 抽出的**纯判据**，无状态、可脱离牌桌单测：
                  WinCheck(和了形判断) / RoundOptions(选项生成) / RoundClaims(鸣牌仲裁) / RoundScoring(结算判据)
mahjong.net       Server(监听/双栈绑定), Session(一连接一线程 + NDJSON 编解码)
mahjong.bot       Bot（补位机器人）
mahjong.test      SelfTest（规则引擎 + 协议回归；`--selftest`）
```

### 为什么把判据抽成纯函数

`Round` 是状态机，早期把「能不能和」「能做什么」「什么时候停止等待鸣牌」「庄家是否连庄」
这类**判据**和状态推进混在一起。后果是：判据只能靠跑整局来验证，
而其中不少缺陷**不会让分数算错、只会让行为偶尔不对**
（例如：没有荣和者时提前收工 → 静默丢掉一次碰/吃机会；连庄条件写错一处 → 分数对但庄家轮错）。

抽成纯函数后，这些判据可以**不构造牌桌、直接断言**，并且刻意做到**正反两面都测**：

```java
eq("荒牌流局庄家听牌 → 连庄",  RoundScoring.exhaustiveBy(0, tp),  true);
eq("荒牌流局庄家不听 → 轮庄",  RoundScoring.exhaustiveBy(0, tp2), false);
```

同时用**实局路径覆盖计数**确认它们不是死代码（见 `SelfTest.simulationTest()` 打印的 `[覆盖]` 行）。

### 鸣牌仲裁：优先级 + 提前收工 + 队列卫生

一张舍张要同时问多家，仲裁分三步，**每一步都有一条容易写错的地方**：

1. **问谁**：`claimOptions(s, from, tile)` 有真选项的才问（只有 `pass` 的不问、也不该拖住别人）。
2. **何时收工**（`RoundClaims.shouldStop`）：都答完 / 超时 / 荣和都收齐 /
   **已到手的最优鸣牌没人能压过**。最后一条是「胡 &gt; 杠 = 碰 &gt; 吃」的另一半 ——
   高优先级一旦成立就**不必再等低优先级的人**，否则平白拖满整个鸣牌窗口
   （实测：能碰的那家已经回了，却因为另一家"能吃但没点"而要等满 3 秒）。
   判据里的「压过」必须与实际仲裁**同一把尺子**（等级 → 座次；同级时离打牌者近的赢），
   否则提前收工会改变赢家。
3. **收工之后**（`Table.dropReplies` + 「type 必须属于本次询问」）：
   被取消询问的那家可能**回包已经上路**。这类回包没法用 `ask_id` 识别
   （老客户端根本不带 `ask_id`），却能：
   - 被下一次鸣牌询问按座位认领 → 凭空按了碰/吃；
   - 被下一巡的 `awaitAction` 当作出牌答复 → **玩家没动就被代打**。

   所以两手都要：取消时把**已在队列里**的废包摘掉（`dropReplies`），
   以及在认领处校验 **`type` 属于本次询问给过的选项** —— 废包的 `chi`/`pon`
   不可能出现在出牌询问的选项里，于是它被丢弃、玩家照样拿到完整 deadline。

### 报文只走 ASCII 码，文案归客户端

服务端是**唯一权威方**，但它**不负责措辞**。报文里的词汇性文本一律只发稳定 ASCII 码：

| 报文里 | 发什么 | 谁翻成中文 |
| --- | --- | --- |
| `yaku[].code`（+ 参数化役种的 `tile`） | `"riichi"` / `"yakuhai"` + `"5z"` | 客户端语言文件 `yaku.*` |
| `limit` | `"mangan"` / `"kazoe_yakuman"` | `limit.*` |
| `reason` | `"exhaustive"` / `"four_kans"` | `reason.*` |
| `error.code` / `error.arg` | `"unknown_cmd"` + `"frobnicate"` | `error.*`（模板带 `%1`） |
| 牌码 | `"1m"` / `"0p"` | `tile.*` |

- 码表集中在 `rules/YakuCodes.java`（中文名 → 码的**唯一**映射处）。`Evaluator` 内部照旧用中文名
  （日志与自测可读），只在 `Round`/`Table` 发报文时翻成码。
  **新增役种必须登记**，否则整场模拟的自检会因 `misses() > 0` 失败。
- 中文只留在三类**用户数据**字段：`seats[].name`（玩家名）、房间名、`chat.text`。
  这三类是不可枚举的，且本来就是"任意文本"。
- 客户端把码翻译成文案（`src/i18n/Lang.cpp`），**语言文件是独立的运行期资源**
  （`assets/i18n/<locale>.json`，目录优先 → qrc 兜底）→ **改文案不用重新编译**，
  加一门语言只是多一个 json。
- 这样分层的收益：报文可 grep / 可断言（`tools/e2e-test.mjs` 逐条审计非 ASCII），
  端到端不再依赖字符集，服务端也不必背一份"给玩家看的措辞"。

`tools/check-i18n.mjs` 是这条链路的**静态哨兵**：以服务端词表为权威，
逐码核对客户端语言文件有没有对应文案，缺一条即失败。

### 并发模型

- 每个连接一个读线程（`Session`），把 `cmd` 转成消息投递到该座位的阻塞队列。
- 每张桌子一个 `Table` 线程（游戏循环），串行推进状态机；所有状态修改都在该线程内，天然无锁。
- 需要等待玩家决策时，`Table` 调用 `seat.awaitAction(deadline)`，阻塞在队列上；超时按规则代打。
- 出站消息投给每个 `Session` 的写线程队列，避免慢客户端阻塞牌局。

### 训练接口：策略注入 + 自对弈

目标：让「用机器学习做一个电脑玩家」这件事**只碰一个接缝**，且不破坏任何既有约束
（规则只在服务端、零第三方依赖、五层验证）。协议与数据格式的权威描述在
`docs/PROTOCOL.md` §8，这里只说设计取向。

**为什么先做接口而不是先训模型。** 训练一个麻将策略的真正成本不在网络结构，而在
「特征对不对、标签从哪来、怎么证明变强了」。这三件事都要求服务端先能
**可复现地批量自对弈**并把每一步的（信息集、合法动作、选择、结果）落成数据：

| 需求 | 没有接口时 | 有接口后 |
| --- | --- | --- |
| 采数据 | 只能爬客户端报文（延迟、抖动、还要写协议客户端） | `--selfplay N --out dir` 直接出 JSONL |
| 证明变强 | 「感觉打得不错」 | `--rotate` 配对（同牌山、四座位轮转）+ 顺位/和了率/放铳率 |
| 复现一局 | 种子来自时钟（有意为之的安全设计） | `debugDeterministicSeed` + 预算好的每场种子 |

**接缝的形状。** 状态机的两处询问（自家摸打、鸣牌段）汇到一个漏斗
`Table.decideBot(seat, Decision)`；`Table.policy[seat] == null` 时走内置机器人，
所以**功能引入前后生产行为逐字节相同**（自检 597 → 642 项，旧用例全绿）。

刻意分成三个接口而不是一个：

- `Policy`（拿得到 `Round`）—— 内置机器人要用 `Round` 的公开辅助方法算牌效；
- `ActionPolicy`（**拿不到** `Round`）—— 训练侧只实现这个。这不是洁癖：
  进程内能读到 `Round.hand[other]`、`Round.wallOrder()`、`uraIndicators()`，
  一个不留神就会训出一个**作弊**的模型，而且训练/评测同时失效、还查不出来。
  把入口设计成"根本拿不到"，比写文档提醒可靠。
- `PolicyFactory`（每局一份实例）—— 并行自对弈会打乱"哪一局先跑"，
  只要实例跨局带状态（RNG、缓存），同种子就不再可复现，配对评测也就失效了。

**反作弊是一等的正确性属性，所以它有测试。** 观测的不变式是
「置换别家手牌 / 别家振听 / 别家门清后，同一座位的观测 JSON **逐字节相同**」，
配一条**正向对照**（他家立直、自家振听变化**必须**被反映）——
没有对照的话，一个"冻结的观测"也能让不变式通过。`tools/selfplay-check.mjs`
再在**产出端**用独立实现核一遍字段白名单，防止后来者顺手往观测里加字段。

**信息集纪律的一个真实收获。** 观测构造最初调用 `Round.isFuriten()`，
它内部会跑 34 次向听 DFS；但自家回合的手牌是 14 张，而 `Agari.waits` 按 13 张定义
（逐张补一张看是否和了形，14 张补完是 15 张、永不成和）→ 听牌集合**恒为空**，
那一刻它完全等价于 `furitenTemp || furitenPerm`。一次纯浪费的热路径 DFS。
修法不是"加缓存"，而是**用与规则等价但更便宜的定义**，并在注释里把等价性写清楚。

> 顺带一条度量教训：修掉它只快了约 10%（16 场 61.6 s → 55.4 s），
> 而我最初按"冷 JVM 的几次采样"估成了 90%。真正把账算清的是
> ① 单核跑 **64 场**（摊掉 JIT），② 一个直接测 `Observation` 构造的微基准
> （0.85 µs/次）—— 两者一起才能说"接口开销可忽略"。
> 结论：**批量基准要跑到稳态，否则会把 JIT 预热当成回归。**

**奖励为什么是回填的。** 麻将的奖励天然稀疏（一局打完才知道谁和了），
`TraceRecorder` 因此先缓冲策略行，小局结束时补 `hand_*`、整场结束时补 `placement`。
顺位在同点时按**座次先后**拆开，保证恒为 `1..4` 的排列 —— 否则"平均顺位"
会被同点挤掉一个名次，配对比较失去意义。

**成本。** 观测构造 0.85 µs/决策 + 动作展开 0.15 µs（记录时再加 9.5 µs 的 JSON），
整场约 800 次决策 → 不记录时 **0.8 ms/场**、记录时 8.4 ms/场（相对 3.6 s/场可忽略）。
也就是说"生产路径也走同一段观测代码"这个设计**不花什么钱**，
换来的是"训练时好用、上线不一样"这类问题不可能出现。

**下一步的形态选择**（`PROTOCOL.md` §8 那张表）：训练阶段用**外部进程当玩家**
（零服务端改动、信息集由协议保证、Python 生态随便用）；到了要发布的形态再导出权重、
用**纯 Java 手写前向**把策略嵌回进程内（保住 `java -jar` 自包含）。

### teacher（内置机器人）的三层取舍

内置 `Bot` 有两个身份：**补位机器人**（大厅里 `fill_bots` 用）与**训练用的 teacher**
（行为克隆的标签来源）。所以它的水平直接决定"学出来的策略长什么样"——
一个只会"向听优先"的 teacher 教不出会防守的学生。

它现在按三层决策，每层都写成**只吃公开信息**的静态判据（{@code Bot.HandState} 是那份信息），
于是自检可以**直接构造局面**断言取舍，不必跑一整局碰运气：

| 层 | 判据 | 具体取舍 |
| --- | --- | --- |
| **牌效** | `HandEval` + `Visible` | 向听 → 进张**枚数按实际可见牌扣**（旧版永远按"满 4 张"算）→ 听牌时优先良形（两面，`goodWaitTiles`） |
| **押し引き** | `Danger` | 有人**立直**且自己 2 向听以上 → 弃和：在"不增加向听"的一组里挑最安全的（现物 → 筋/壁 → 无信息） |
| **打点与役** | `Round.scoreIfWin` | 同效率时留宝牌；立直 vs 默听按"**不立直**能值多少番"决定；鸣牌前先确认鸣完**还有役** |

三条最容易踩的坑（都真踩过，写在断言里）：

- **弃和时只能看立直家**。`Danger.worst` 对四家取最坏，而没人立直的对手"手里是什么样"无从判断，
  把他们算进来会让每张牌**一样危险**、把立直家现物那份真正有价值的安全度淹掉
  （实测：只有一家立直时，现物和筋的分一样，弃和就选不出安全牌）→ 弃和走
  `Danger.worstAgainstRiichi`，进攻才用 `worst`。
- **鸣牌要把役算进去**。鸣牌打掉门前清（也就打掉立直这条路），鸣完若是无役牌型，
  这手**永远和不了** —— 旧 teacher 只看"向听是否变好"，会心安理得地鸣出这种手。
  `Bot.hasYakuPlan` 只认四种可靠计划：役牌 / 断幺九（食断规则下）/ 混一色·清一色 / 对对和；
  三色、一通这类形状役**故意不查**（便宜近似查不准，宁可漏掉一些其实有役的鸣牌）。
- **默听的前提是"不立直也能和"**。用 `scoreIfWin(..., assumeRiichi=false)` 一问便知；
  没别的役时不立直就根本和不了，必须立直。判据只有一条：不立直已经 ≥4 番才默听
  （立直只 +1 番 + 里宝期望，而默听保留手替え/换听的自由度）。

**成本**：良形分类要对每个听牌张做一次和了形分解，因此决策比"纯向听+进张"贵。
`chooseDiscard` 因此分两遍：先用便宜的判据（向听 / 危险度 / 宝牌）圈定"向听最小的那一组"，
贵的评估只跑这一组 —— 单核自对弈 6.2 → 4.96 秒/场（旧 teacher 3.6 秒/场，换来上面三层取舍）。
L1 自检相应从 77 秒涨到 97 秒（整场模拟用例变慢）。

**刻意保留的简化**：teacher **从不开杠**（大明杠"简化：不开"）——
这条被自检依赖（岭上那条路径靠 `Bot.debugAlwaysKan` 强制覆盖），
所以"该不该开杠"不在当前取舍范围内，是下一步的事。

### 牌面绘制

牌面走 **SVG 矢量素材**（`client/assets/tiles/<牌码>.svg`，38 个：37 种牌 + 牌背），
**取不到素材时回退到 `QPainter` 程序化绘制**——删掉整个 `tiles/` 也不会白屏：

- 查找顺序：exe 同级 `tiles/` → qrc 内嵌 `:/tiles/` → 程序化绘制。
- 换素材只需保持**文件名（= 牌码）与 `viewBox="0 0 300 400"`**，**改完重启客户端即生效，无需重新编译**。
- 只有 `TileRenderer` 感知素材，`TableView` / 牌河 / 副露 / 手牌等调用方完全无感。

回退路径（同时也是占位符的绘制基准）：

- 牌面：象牙白圆角矩形 + 单层描边（**扁平，无厚度层、无立体感**）。
- 万子：上部汉字数字（一~九），下部红色「萬」。
- 筒子：按点位排列的同心圆（1筒大圆带内圈，2~9筒按标准点位）。
- 索子：按点位排列的绿色竹节（1索画一只绿色鸟形）。
- 风牌：東/南/西/北 黑色大字；三元牌：白（蓝框空白）、發（绿）、中（红）。
- 赤五：数字/图案用红色。
- 牌背：深绿纯色 + 斜纹（无渐变、无厚度层）。

尺寸**由内容反推**（不是先定一个"好看的方块"再往里塞）：`TableView::computeLayout()` 先按盘内要放的
东西（宝牌指示牌行 = 5 张、四家点数、场次、立直棒）与盘外要留的东西（四家牌河各 3 行 + 余量）
算出风盘 `cw/ch`，再钳制到外圈预算（`盘半 + riverExtent ≤ 屏半 − 内边距 − 手牌厚`），最后把 `ch`
补到接近 `cw`。**牌河、手牌、副露的尺寸都由 `手牌宽 tw` 按固定比例推出**（牌河 0.798 / 宝牌 0.76），
不再随窗口高度单独缩放。完整不变的约定见 `AGENTS.md` §6「风盘尺寸必须由内容反推」。

**默认预设 = M.League**（`rules.preset = "mleague"`，逐条依据 `docs/日本麻将.md` 2026-09 版里
标注的 M.League 规则；协议字段与三套预设的速查表见 `docs/PROTOCOL.md` §5）。
`Rules` 先铺预设、再让报文里的单项字段覆盖，所以「选 M.League 再把某一条改掉」是支持的。

M.League 默认取舍：

- 有食断、有后付（アリアリ）、有里宝牌、有杠宝牌、有赤宝牌 3 张、无古役、常时一番缚。
- **4 种"两倍役满"役不加倍**（国士无双十三面 / 四暗刻单骑 / 纯正九莲宝灯 / 大四喜）：
  它们仍是**各自的役种名**，只是计 1 倍 —— 役种命名与取值是两件事。
- **无累计役满**：番数 ≥13 且无役满役时按**三倍满**（基本点 6000）计，普通役的上限就是三倍满。
- **切上满贯**：3 番 60 符、4 番 30 符（基本点 1920）按满贯计。
- **连风雀头 2 符**（一般规则是自风 2 + 场风 2 = 4 符）。
- **无中途流局**（九种九牌 / 四风连打 / 四家立直 / 四杠散了都不流局），
  三家和了改判**头跳**（`head_bump`）。
- **无击飞、无和了止、无流局满贯、无西入**：半庄打到南 4 局庄家轮庄为止。
- **立直放宽**：不要求手上 ≥1000 点、也不要求残牌 ≥4，但**摸到海底牌之后不可立直**。
- **立直后的暗杠**要求「所听牌不变」**且「面子构成不变」**（允许役种增减）。
  判据取"这 4 张牌在手里没有任何同花色的邻居（±1/±2）"，即它不可能被当成顺子的一部分；
  这是**保守**判据（宁可多禁掉个别罕见形状，也绝不放行会改变面子构成的暗杠），
  文档里的 4 个例子全部落在正确的一侧（见 `Round.ankanKeepsShape`）。
- 包牌：**四杠子也算包牌**（由他家的舍张大明杠完成第 4 个杠）；判定大三元/大四喜时**计入已公开的暗杠**；
  包牌只承担**被包的那一役**（《天凤》才承担复合后的全部役满）。
- 精算 =`(点数 − 30000)/1000 + 马点(10-30) + 头名赏(20)`，**同点平分对应名次的加点**。
- 人和默认关闭（`renhou: "off"`）、禁止食替、不听罚符 3000。

### 终局与精算：M.League 原文（口径依据）

用户裁定时给出的 M.League 规定原文（**本项目的依据**，逐字保留）：

> 竞技顺位根据半庄结束时合计得分的多少来决定。
> 顺位点是指根据半庄中的竞技顺位进行加減的点数，本规定采用以下方式。
> 1位+50,000点　2位+10,000点　3位▲10,000点　4位▲30,000点
> 持点和顺位点均按1000点＝1分换算并统计成绩。
> 【例】35,800点的2位→+5.8p+10.0p（顺位点）=+15.8p
> 41,600点的1位→+11.6p+50.0p（顺位点）=+61.6p
>
> 因流局导致半庄结束时，立直棒加算给第一位（Top者）。
>
> 半庄结束时若出现同分，则拆分顺位点。3人同分时的尾数，由更接近起家的一方获得更多点数。
> 因流局结束时的立直棒由相关者均分。3人时，将1000点分为400、300、300，若无法整除则按此倍数分配。
> （2000点时为800、600、600）。与顺位点相同，更接近起家的一方获得更多点数。
> 且如果即使有三人重新分配余棒后，持点不相同，他们三人仍然同顺位，由更接近起家的一方获得更多顺位点。

对应到实现（**已一致**的部分）：
- 「1位+50,000」= **马点 30 + 头名赏 20**（`uma {30,10,-10,-30}` + `oka = (30000−25000)×4/1000 = 20`），
  所以原文的 50/10/−10/−30 与本项目的 `uma` + `oka` 是同一套东西；上面两个例子逐位一致。
- **终局余棒分配**（`RoundScoring.endGameSticks`，批次三）：1 位只有一家就全给它；**并列第一**时
  由**相关者**（并列的那几家）均分 —— 按 100 点为单位向下取整、尾数归**更接近起家**的一方，
  与原文逐字一致（3 人 1000 → **400/300/300**、2000 → **800/600/600**）。
  ⚠ 只有「**流局**结束」才走这一支：和了结束时和牌者已把供託收走（`sticksLeft = 0`），
  所以 `Table` 里那句 `if (sticks > 0)` 天然只对应原文说的「因**流局**导致半庄结束时」。
  ⚠ 「更接近起家」= **座次更小**（seat 0 = 起家），与 `settle()` 里"同点按座次先后定名次"同一把尺子。
  ⚠ 这里只动**持点**：并列的几家仍然**同顺位**，名次不由这个分配改变。

**顺位点拆分**（同分）与**余棒**：
- 「同分则拆分顺位点；3 人同分的尾数由更接近起家的一方获得更多点数」→ `rules.tie_split_point`
  （M.League 开）：按名次区间**平分**该区间的马点与头名赏。⚠ 原文的"尾数归更接近起家者"只在
  **不能整除**时才有差别（本项目的马点是整数、`oka = 20` 三人分才有 0.1 分级尾差），
  本项目按平分算（`AUDIT §1.10` 已裁定"精算数值不改"），差别已登记在此。
- 「即使重新分配余棒后持点不同，三人仍然**同顺位**」→ 余棒分配**只动持点**，
  名次仍由 `settle()` 按分数排（同分同区间），别把名次也拆了。

### 其它已裁定的口径

- **食い平和（副露 + 无符之形）自摸按 30 符**（本作口径；`document` 原文只写了荣和 30 符）。
  注意**平和是门清役** —— "食い平和"拿不到平和这一役，它只是"副露手没有符"的形。
- **食替的禁打集合**（`docs/日本麻将.md` §食替 只写了「現物」与「順子另一边」两句话，
  具体形状由本作按"鸣牌白鸣"的禁止理由推出来，实现在 `RoundOptions.kuikaeForbidden`）：
  - **現物食替**：所吃/所碰的那张本身；
  - **筋食替**：这副顺子里**从手里拿出的那两张**还能配成的**另一副**顺子的第三张
    （吃 3m4m+2m → 禁 5m；吃 3m4m+5m → 禁 2m，**两侧都要算**）；
  - **坎张吃没有筋食替**：4m6m 吃 5m 时这两张唯一的完成形就是被吃的那张本身
    （切 3m 或 7m 都不是"用同一组手牌重排"，不构成白鸣）。
  - 服务端**自己校验**这份集合（`Round.discardAllowed`），下发选项只是提示，不是安全边界。
- **默认思考时间统一为 `20+5`**（额外 20 s + 每巡 5 s）：`Rules` 的字段初值与客户端大厅默认值
  **已经一致**（批次三把 `Rules` 的 `0+15` 改成 `5000/20000`，客户端本来就是 `20+5`）。
- **和了止 + 听牌止**：All Last 庄家**达到一位必要点数且为 1 位**时，「和了」与
  「**荒牌流局时庄家听牌**」都结束对局（`RoundScoring.stopAtAllLast`）。
  ⚠ 流局满贯**不算**听牌止（原文只说"荒牌流局"，而流局满贯按和了结算）。
- **一位必要点数**：M.League **不要求**（0）；《天凤》《雀魂》为 **30000**；
  并新增房主**自选填写**（字段 0 = 不要求）。它决定两件事：①All Last 轮庄后是否进延长战
  （东风战→南入、半庄战→西入，**没有北入**）②All Last 庄家能否和了止/听牌止。
  ⚠ 它与 `return_score`（**精算**基准）是两个概念：《雀魂》= 30000 vs 25000，
  别再拿精算基准当门槛（延长战那一支原来就是这么写的）。
- **头跳与三家和了同时打开时，头跳优先**（自定义规则才会碰到）：头跳一旦把多家荣和归约成
  最近一家，「三家**同时**荣和」这个前提就不存在了。三套预设本来就互斥
  （mleague 头跳 / 天凤三家和了 / 雀魂两个都不开）。
- **多家荣和时立直棒与「本场加点」都只归距放铳者最近的一家**（文档 §和牌 L794 的《天凤》口径；
  文档没给《雀魂》的另一套，而 M.League 头跳下根本到不了这里）。
  实现在 `Round.agariRon`：`useSticks` 与 `useHonba` 都只在 `winners[0]` 那一次结算里生效。
- **燕返（立直宣言牌放铳 → 立直不成立）只对「首次放置」的宣言牌成立**（文档 §立直 L893 +
  L1291-1293）：宣言牌被鸣走后横置顺延到该家下一张打出的牌，那张被荣和**不算**燕返。
  实现在 `Round.agariRon`（撤销立直 + 退回 1000 点 + `sticks--`），
  客户端按报文里的 `agari.riichi_void` 清标记与供託 —— **立直成不成立是规则判定，
  客户端不许自己推断哪张是宣言牌**（AGENTS §2.1）。

《天凤》/《雀魂》可用 `rules.preset` 切换（`tenhou` / `majsoul`）；差异速查见 PROTOCOL §5。

**不做 / 妥协**（见 `docs/AUDIT.md`）：

- M.League 的**程序性判罚**（扣 20/60 点、诈立判罚、点棒授受订正）与"重大犯规"，属于线下裁量，不实现。
- 形式听牌的"自家已用尽等待牌"两种判定（《天凤》只看手牌 / M.League 连同副露）未区分；
  本项目按"只要 `Agari.waits` 非空就算听牌/可立直"处理（= 《天凤》那一侧；
  ⚠ M.League 是**连同副露**计算，属**更严**的一侧 —— 别把这里写成"更宽松"）。
- 《雀魂》的「国士无双可抢暗杠」与「天和时国士无双视作十三面」未实现（只影响《雀魂》预设）。
- 杠宝牌的**翻牌时机**：M.League 是"杠成立后立即翻开"（本项目按此实现）；
  《天凤》对明杠/加杠是"随后打牌时或摸岭上前翻开"，本项目不区分（只影响信息公开时机，不影响算分）。

### 振听：三种都要记，而且**舍牌要记一辈子**

`docs/日本麻将.md` §振听 把振听分三种，三种在实现上落在三个不同的位置 ——
这是一次审计里发现**三条全都不成立**的地方（`furitenTemp` / `furitenPerm` 只有清除、从来没人置位；
舍张振听看的是牌河，而被他家鸣走的舍牌**已经不在牌河里**）：

| 种类 | 触发 | 解除 | 实现位置 |
| --- | --- | --- | --- |
| **舍张振听** | 听牌张里有一种是**自己曾经打出过**的（含**被他家吃碰杠走**的） | 改变手牌后，所听的牌都没被自己打出过 | `Round.discardKindsEver` + `ownDiscardKinds` |
| **同巡振听** | 他家打出能和牌而**自己没和**（含超时未答） | 自家下一次摸牌时 | `Round.claimPhase` 的见逃记账 + 出牌段开头的清除 |
| **立直振听** | **立直**状态下见逃荣和或**见逃自摸** | 本局结束（`furitenPerm`） | 同上两处，额外条件 `riichi[seat]` |

要点：

- **「曾经打出过」≠「牌河」**。鸣牌是"移动"不是"复制"（见 AGENTS §2.2 的 `called_index`）：被鸣走的牌
  会从 `discards[]` 移除，但它**仍然是你的舍牌**。所以振听要一份单独的账
  （`discardKindsEver[4][34]`），出牌时只在唯一的记账点 `Round.recordDiscard` 里累加。
  ⚠ 别把 `ownDiscardKinds` 当成"牌河的镜像"用 —— 它只服务振听。
- **见逃必须真的记一笔**：`claimOptions` 只在**不振听**时才下发 `ron`，所以"给了 ron 却没和"
  就是一次货真价实的见逃（超时未答同样是见逃）。记账发生在鸣牌仲裁之后、逐座位判断。
- **立直见逃自摸**：立直家摸到自己的和了牌却不和（`turnOptions` 里给了 `tsumo` 而最终没和）
  → `furitenPerm` 置位，本局之内再不能荣和。这是"为了做大牌而见逃"在规则上的代价。
- ⚠ **已知偏差**：`ron` 只在有役时才下发，所以「无役的和了形被见逃也触发同巡振听」
  （《天凤》的做法）**没有**实现 —— 那一刻服务端根本没问，也就没有"见逃"事件可记。
  同理，已经在振听里的立直家不会被记成立直振听（他本来就没有 `ron` 选项，谈不上"放弃"）。
  两者都只在很窄的局面下与《天凤》不同，且都不会让界面显示错（`win_note` / `furiten` 照常）。
- 回归：`SelfTest.furitenRuleTests`（① 舍张振听含被鸣走的舍牌 + 改变手牌后解除；
  ②③ 用"见逃策略"跑整场，逐座位检查「见逃之后本巡/本局之内一直振听」的不变式，
  并断言**确实造出过**见逃机会 —— 否则那两条断言是空转）。

## 对局记录与回放

需求：服务端存下整场对局（起始牌山、每一次摸牌/出牌/鸣牌/立直/荣和/流局、以及玩家对话），
提供受控的读取接口与唯一标识符；客户端能可视化回放并逐操作/逐巡/逐小局导航，
还要能看**整副牌山（136 张）**的进展。

**服务端**（`server/.../replay/`）：

```
Table（牌桌线程）                        Session（连接读线程，可多个）
  send()/broadcast() ──► ReplayRecorder    replay_list / replay_get
                          │  （整场一个，内存里）        │
                          └─► 终局时 store.put() ──► ReplayStore（内存索引 + 落盘 replays/）
```

- **记录**：`ReplayRecorder` 挂在牌桌的两个下行点（`Table.send` / `Table.broadcast`）上，
  记的就是**客户端实际收到的报文**。好处是回放与实时对局走**同一条渲染路径**
  （客户端把同一串事件喂回 `TableModel`），以后新增事件类型回放自动支持。
  聊天也走同一条广播路径 → 与操作**共用一条单调递增的 `seq`**，先后顺序天然稳定。
  小局的牌山快照（136 张、按抓牌顺序）用 `Table.replayNote()` 记成一条**只给回放看**的条目
  （塞进正常报文等于每小局给所有客户端多发 136 个牌 id）。
- **容量**：单场条数（20000）与字节（8 MB）双封顶，超限置 `truncated` 并停止续记；
  库里场数（默认 50）与总字节（默认 96 MB）也双封顶，超出**淘汰最旧的并删文件**。
  实测一场东风战 `--fast` 跑完是 806 条 / 384 KB（丢掉了摸牌的三份广播副本）。
- **安全**：ID 是 CSPRNG 生成的 10 位 base32（≈50 bit），**先校验形状再拼路径**
  （否则 `../../x` 就是目录穿越）；接口只读；列表只回元信息（不含牌山）；
  `replay_get` 单次最多 2000 条；每连接每 10 秒最多 60 次请求；
  非法 ID 与"不存在"回同一个 `replay_not_found`，不区分（免得被拿来探测）。
  ⚠ **回放天然是上帝视角**（四家手牌 + 牌山顺序），拿到 ID 就能看 —— 这是功能前提，
  所以只在**牌局结束后**可读，且 ID 不可猜。
- **性能**：录制只做一次浅拷贝 + 追加（不落盘、不加锁）；落盘在**整场结束后**一次完成，
  且**先落盘再广播 `game_end`** —— 客户端收到结算就会给「看本局回放」按钮，
  那一刻记录必须已经能取（真机 L3 上踩过：先广播后落盘时列表里少刚打完的那一场）。
  读取侧内存索引只存头（含每小局牌山，约 4 KB/场），操作**按需读盘 + 热缓存**
  （最近看过的那几场留内存，按总字节淘汰）。

**客户端**（`model/ReplayModel` + `ui/ReplayWindow` + `ui/WallView`）：

- `ReplayModel` 是纯数据：解析头与操作页，**一趟线性扫描**建好"小局 / 巡 / 牌山归属"索引。
  之后"下一巡 / 跳转第 N 巡 / 上一小局"都是查表；牌山只放 `下标 → 归属` 的紧凑结构。
- 回放画面 = 把事件按序喂给**既有的** `TableModel` + `TableView`（视角可切四家），
  所以牌桌的画法与实时对局完全一致。**跳转 = 从本小局的开头重放**：
  一个小局最多几百条，微秒级，不必给每种事件写反向操作（那才是 bug 温床）。
- 导航单位是**步**（一个逻辑操作）：`round_start` 的 4 条按座位副本折成一步，
  否则一次配牌要按四次"下一步"。
- `WallView`（单开窗口）把 136 张按**抓牌顺序**铺成**一条序列**：**每列 4 张**（自上而下读）、
  每 4 列留一个稍大的空隙，末尾 14 张王牌仍在同一序列里、只是底色不同。
  ⚠ **绝不能按玩家分行**：副露（吃/碰/杠）会改变"下一個摸牌的是谁"，所以任何"一行一家"的排法
  都是错的（第一版就是那么排的，用户直接点了出来）。"4 张一组"只是**阅读分组**，与玩家无关。
  每张牌按**当前步**着色（牌背 = 还没摸到 / 手牌 / 已打出 / 已副露 / 王牌 / 开杠移入王牌），
  底部一条细线是**谁拿走的**归属色（四家混排也认得出归属），当前这一步那张加红框。
  点某张牌可跳到"它被拿走"的那一步。
- **渲染动画只在"前进一个操作"时播**：下一步、播放的每一拍。其余一切跳转
  （上一步 / 换巡 / 换小局 / 跳巡目 / 点操作列表 / 换视角 / 刚载入）都是**静默重建**。
  原因是"跳转 = 从小局开头重放"，若每次都带动画，就会把前几巡的弃牌动画重打一遍
  （用户报的"每回放一个操作，四家都重复打出前几巡的牌"就是这个）。
  实现落在 `ReplayWindow::replayTo(index, animate)`：只有目标恰好是当前步的下一步时才开动画，
  且只对**落在最后一步里**的事件放开；判据在 `TableModel::setSilent()`。
- **操作列表按小局切割**：只装当前小局的步骤（列表标题写明是小局几），换小局才重建，
  当前行 = 本小局里的第几条 —— 一场半庄上千步，一条长列表找不动。
- **每小局结算**：`ReplayModel::roundResultEntry(round)` 定位该小局的 `agari` / `ryuukyoku`，
  播放跨小局时**自动弹出**并暂停播放，**没有倒计时**；工具栏「本局结算」可随时手动打开。
  必须等玩家点确认才进下一局 —— 回放没有"5 秒后自动开下一局"这回事。
- **上帝视角（「显示他家手牌」）的数据存在 `TableModel` 里，不是只存在控件里**：
  牌桌的**布局**（手牌行几格、摸牌槽在哪）是按 `TableModel::concealedCount()` 算的，
  出牌动画的起点也按布局算。数据只放控件里的话，布局用"张数"、绘制用另一份手牌，
  就会各说各话（实测现象：开了他家手牌之后张数不对、牌飞出的格子也不对）。
  - **"知不知道"与"显不显示"是两件事**：真实暗牌**始终**交给模型（`setGodHand`），
    「显示他家手牌」只控制**画不画牌面**（`TableView::setGodVisible`）。
    因为布局与动画起点都要按真实张数算 —— 这与"给不给玩家看牌面"无关。
  - ⚠ **它不能在 `TableModel::reset()` 里被清掉**：回放每次跳转都是
    `reset()` + 从头重放一遍，重放到"出牌"那一步时正需要**上一帧那份**（= 出牌前的手牌）
    来算动画起点。在这里清掉，动画就只能退回"随机挑一格"（真机上就是这么表现的）。
    换一场记录时由 `ReplayWindow` 显式 `clearGodHands()`。
  - **理牌**：上帝手牌在 `setGodHand()` 里就用 `mj::sortTiles()` 排好（与自家手牌的
    `sortHand()` **同一把尺子**）。⚠ 不能用 `QStringList::sort()`：那是字典序，赤五 `0m`
    会被排到 `1m` 前面。
  - **出牌动画起点**：**实时对局里别家的手牌不可见**，手切只能随便挑一格起飞 ——
    那是**故意**的（否则看久了能反推出手牌顺序）。回放没有这个顾虑，而且要求动画与手牌位置一致，
    所以只要手牌已知就**一律**从"这张牌真正待着的那一格"起飞（同码多张取第一张，不再随机）；
    摸切固定从摸牌槽起飞。
  - **回归要跑真路径**：这条 bug 的第一版修法**没生效**，而当时的自检全绿 ——
    因为它自己 `setGodHand()` 再 `applyEvent()`，**绕过了 `ReplayWindow::replayTo` 的
    reset + 重放顺序**。现在自检走 `loadForTest()` + `nextOpForTest()`（与点「下一步」同一个槽），
    并用"把 `clearGodHands()` 加回 `reset()`"做过红证。
- 聊天面板按 `seq` 切分，只显示当前步之前的发言。
- 入口两个：大厅「对局回放」（列表里双击一场，或粘 ID）与**整场总结算**的「看本局回放」
  （`game_start` / `game_end` 里带 `replay_id`，拿不到就隐藏按钮）。
  ⚠ 「看本局回放」**只在整场总结算出现**：牌局还没结束时记录尚未落盘（服务端是终局才写），
  那个按钮点不出任何东西；用户也明确要求"未结束时不该提供回放按钮"。
  回放窗口**自己开一条连接**，所以对局进行中也能看别的场次，不影响当前牌局。



## 材质包与个人设置

需求：把**牌面/牌背、桌布、立直棒、UI 字体**做成可替换的"材质包"，
并把**服务器地址/端口、昵称、材质包路径**持久化；三者都要**足够鲁棒**。

**个人设置**（`model/Settings`）：

- 四项：`host` / `port` / `name` / `pack`。位置：`MAHJONG_SETTINGS` 环境变量 →
  exe 同级 `settings.json`（绿色版语义）→ 用户配置目录（exe 同级不可写时）。
- `load()` **永不失败**，这是刻意的设计而不是"容错凑合"：
  | 情况 | 行为 |
  | --- | --- |
  | 文件不存在 | 按缺省值生成一份（用户知道去哪改） |
  | 不是合法 JSON | 备份成 `.bak` 再重新生成（不直接扔用户的文件） |
  | 某个键缺失/类型不对/超范围 | **只重置那一个键**，其余保留 |
  | 认不出的键 | 原样保留并回写（向前兼容） |
  | 读不出来（权限） | 用缺省值跑这一回，**不覆盖**文件 |
  `repaired` / `note` 两个输出参数把"改了什么"回报给界面与启动日志 ——
  静默改掉用户的东西比报错更糟。写盘走"临时文件 + 改名"，写到一半崩了不会留半个 JSON。

**材质包**（`model/Theme` + `ui/TileRenderer` / `TableView`）：

- 包 = **目录**或 **zip**。zip 走 Qt 私有 API `QZipReader`，并且做成**可选能力**：
  CMake 检测到 `Qt6::CorePrivate` 就定义 `MAHJONG_HAVE_ZIP=1`，否则只支持目录包、
  照常编译（"换个 Qt 就编不过"这种事不能发生）。其它归档格式（7z/tar.gz/rar）不做 ——
  Qt 没有读取 API，不值得为它引第三方库。
- 清单 `theme.json`：键 = 类别，值 = 包内**相对文件夹**（`/assets/tiles` 与 `assets/tiles` 等价）。
  **没写的类别用默认**。路径过 `sanitizeRel()`：盘符、`..`、UNC 一律拒（材质包是第三方内容，
  这是最重要的一道安全闸）。
- **逐类、逐张回退**：类别目录缺失/为空/文件坏，只影响它自己；牌面**逐张对应**，
  绝不"抓一张图顶上别的牌"（踩过：`tiles` 目录里"取第一张图当牌背"会把 1m 画成牌背 ——
  牌背只认精确的 `back.<后缀>`，除非作者给了**专用**的 `back` 目录）。
- 矢量优先（缩放不糊），位图**拉伸铺满**目标矩形；两者可混用。
- 接进渲染链的方式很轻：`TileRenderer` 的素材查找变成
  **材质包 → exe 同级 `tiles/` → qrc → 程序化绘制**，桌布/立直棒在 `TableView` 里
  各加一个"有图就画图"的分支。换包后必须 `TileRenderer::clearAssetCache()`，
  否则缓存里还是上一批图。

## 牌面渲染的性能：位图缓存

`QSvgRenderer::render()` **每次调用都重新栅格化一遍矢量**。出牌动画 16ms 一帧、每帧重画整张桌子
（四家手牌 + 四家牌河 + 副露 + 宝牌行 ≈ 一百多张牌；牌山窗口 136 张），于是每秒要栅格化上万次 ——
实测 **28~32 ms/帧**，已经超了 60fps 的 16.7ms 预算，表现就是"动画轻微卡顿"。

`TileRenderer` 因此按「牌码 + 目标**设备像素**尺寸」缓存栅格化好的位图（`pixCache()`，
上限 512 张、满了整体换代），每帧只剩 blit：**28.45 → 8.43 ms/帧（3.4×）**，缓存只占 15 张
（牌在同一界面里只有几档尺寸）。三个必须做对的点写在 `TileRenderer.cpp` 的注释里，最容易踩的是：

- **键要用设备像素**（`deviceTransform()` 取缩放），否则高 DPI（本机 1.5×）会拿到低分辨率的图；
- **旋转不进键**：位图正着栅格化，交给调用方画笔的旋转变换整体转（90° 整数倍无损）；
- **贴回去必须用设备像素比**（`setDevicePixelRatio` + `drawPixmap(QPointF, pm)`）。
  用 `drawPixmap(rect, pm, srcRect)` 会按逻辑尺寸**再缩放一次**，差零点几像素就触发重采样 ——
  实测那样做牌面边缘会糊一圈（与矢量直画差 12.9% 的像素）。

**代价（说清楚）**：缓存光栅层与矢量直画相比，边缘的亚像素抗锯齿有极小差异（整数像素网格 vs
目标矩形的分数坐标）：实测平均通道差 19，**差 >128 的只占 0.068%**，肉眼看不出，换来 3.4× 帧率。
Qt Quick / 浏览器 / Skia 缓存图层都是这个取舍。要像素级一致的旧行为：`MAHJONG_NO_TILE_CACHE=1`。

## 天鳳牌譜导出

需求：把本项目记录的对局导出成**天鳳牌譜格式**（参考 <https://github.com/wuye999/tenhou>）。

- **格式选了参考项目那一套**：`tenhou.net/6` 的 `#json=` 链接（`model/TenhouLog`）。
  每个小局 17 个元素：`[场局次, 本场, 供託]`、四家点数、表ドラ、裏ドラ、四家配牌（各 13 张）、
  四家取牌、四家出牌、结果。牌号用天鳳的两位数编码（11..19/21..29/31..39/41..47，赤五 51/52/53）；
  出牌里 `60` = 摸切、`"r60"`/`"r<牌号>"` = 立直宣言。**庄家配牌的第 14 张算作他的第一次摸牌**
  （天鳳的语义）—— 这条不写对，整条摸打序列都会错位一格。
- **导出放客户端**：`ReplayModel` 里已经有全部需要的数据（四家配牌、逐张摸打、宝牌、结算），
  所以**协议与服务端一行未改**。数据来源全是既有字段，没有新增协议字段。
- **完整牌谱 = mjlog XML**（`TenhouLog::buildMjlog`）：上面那份瘦格式没有副露，所以再写一份天鳳原生的
  `mjlog`，**鸣牌/立直/和了细节都不丢**。几个必须按公开实现对齐的点（自检里用**照抄的解码公式**反过来解）：
  · 摸牌/打牌把**牌号写在标签名里**：`<T{id}/>`…`<W{id}/>` 是 0..3 家摸牌、`<D{id}/>`…`<G{id}/>` 是打牌；
    所以**摸切必须复用刚摸到的那张的牌号**（公开实现就是靠这个判断摸切）；
  · `<N who m/>` 的 `m` 是位域：吃 `(pattern<<10)|三家副本偏移`、碰/加杠 `(pattern<<9)|(缺的那张副本<<5)`、
    杠 `(代表牌号<<8)|相对座位`（暗杠相对座位 = 0）；
  · 立直 `<REACH step=1/>` 必须在宣言牌**之前**、`step=2` 在其后；
  · 牌号是 0..135 的**唯一**编号 ⇒ 我们自己按"每个种类 4 张副本"分配（赤五固定 0 号副本），
    鸣牌里"手里那几张"要**优先复用刚摸到的那张**，否则一个碰会要出第 5 张同种牌。
- ⚠ **如实说明的两处限制**：① 不写 `<SHUFFLE>`（天鳳把牌山打包成一个没有公开规范的 seed；
  而这份格式里每次摸牌都带牌号，牌山本来就是冗余的）；② 不写 `yaku` 属性（天鳳的役种是数字 id，
  那张表无法在本环境核对，写错等于报错役）—— 家、手牌、和了牌、宝牌/里宝、符数/收支都在。

### 结算界面的牌面示意（字体方案）
牌局中的牌桌走 **SVG 矢量素材**（见上）；**结算界面改走内嵌字体 + OpenType 连字**，两者互不影响。

- 字体 `I.MahjongJP.otf`（Unicode 麻将牌字形），只用 `liga` 特性，**默认生效**。
- `ResultDialog::schematicOf()` 把和牌数据拼成字体能识别的牌码串，
  用控制字符编码多行结构（`U+001F` 行间 / `U+001E` 标签 / `U+001D` 旁挂），
  渲染成「标签 + 牌面」多行：**手牌 / 宝牌指示牌 / 里宝指示牌**
  （数据全部来自既有 `agari` 事件字段，**未新增协议字段**）。
- 和了牌**不并进手牌**：用固定 44px 间隔（= 一个整牌位）空出一格单独摆。
  不靠空格凑宽度——字体空格的字宽并不等于一个牌位。
- **两种表示并存**：牌面示意在上，原文字结算在下；字体不可得或串含非法字元时
  只显示文字，**不会出现空白或错牌**。

为什么不用字体直接画牌桌：字体渲染的是**固定字形**，而牌桌需要按座位旋转、
区分手牌/副露/牌河并做避让布局，SVG + `QPainter` 变换更合适；结算是一次性静态展示，字体最省事。
