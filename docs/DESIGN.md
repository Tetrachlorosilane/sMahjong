# 立直麻将 总体设计

## 目标

- **服务端**：Java 21，零第三方依赖（只用 JDK 标准库），可编译成单 jar 运行于 Ubuntu。唯一权威方：洗牌、配牌、摸切、鸣牌、和牌判定、役种/符数/点数、振听、流局、连庄、精算。
- **客户端**：Qt 6 Widgets + C++17，MinGW 构建，运行于 Windows。只负责：绘制牌桌、收集操作、播放事件反馈、与服务端通信。**不做任何规则判定**。

## 目录结构

```
mahjong/
├─ docs/          规则原文、协议契约、设计、部署
├─ server/        Java 服务端（build.sh 供 Ubuntu 使用）
├─ client/        Qt6 C++ 客户端（CMake）
└─ tools/         本地联调脚本（起服务端 + 机器人）
```

## 服务端分层

```
mahjong.util      Json（手写零依赖解析/序列化） / Log
mahjong.core      Tiles（牌编解码）/ Meld（副露）/ Rules（规则配置项与校验）/ Wall（牌山 + 王牌账）
mahjong.rules     Shanten(向听) Agari(和了形分解) Evaluator(役种 + 符 + 高点法)
                  Payments(点数授受) WinContext(和了上下文) YakuCodes(中文名 ↔ ASCII 码)
mahjong.game      Round(一局状态机) Table(房间/座位/线程)
                  ── 以下四个是从 Round 抽出的**纯判据**，无状态、可脱离牌桌单测：
                  WinCheck(和了形判断) / RoundOptions(选项生成) / RoundClaims(鸣牌仲裁) / RoundScoring(结算判据)
mahjong.net       Server(监听/双栈绑定), Session(一连接一线程 + NDJSON 编解码)
mahjong.bot       Bot（补位机器人）
mahjong.test      SelfTest（规则引擎 + 协议回归；`--selftest`）
```

### 为什么把判据抽成纯函数

`Round` 是状态机，早期把「能不能和」「能做什么」「什么时候停止等待鸣牌」「庄家是否连庄」
这类**判据**和状态推进混在一起。后果是：判据只能靠跑整局来验证，
而其中不少缺陷**不会让分数算错、只会让行为偶尔不对**
（例如：没有荣和者时提前收工 → 静默丢掉一次碰/吃机会；连庄条件写错一处 → 分数对但庄家轮错）。

抽成纯函数后，这些判据可以**不构造牌桌、直接断言**，并且刻意做到**正反两面都测**：

```java
eq("荒牌流局庄家听牌 → 连庄",  RoundScoring.exhaustiveBy(0, tp),  true);
eq("荒牌流局庄家不听 → 轮庄",  RoundScoring.exhaustiveBy(0, tp2), false);
```

同时用**实局路径覆盖计数**确认它们不是死代码（见 `SelfTest.simulationTest()` 打印的 `[覆盖]` 行）。

### 鸣牌仲裁：优先级 + 提前收工 + 队列卫生

一张舍张要同时问多家，仲裁分三步，**每一步都有一条容易写错的地方**：

1. **问谁**：`claimOptions(s, from, tile)` 有真选项的才问（只有 `pass` 的不问、也不该拖住别人）。
2. **何时收工**（`RoundClaims.shouldStop`）：都答完 / 超时 / 荣和都收齐 /
   **已到手的最优鸣牌没人能压过**。最后一条是「胡 &gt; 杠 = 碰 &gt; 吃」的另一半 ——
   高优先级一旦成立就**不必再等低优先级的人**，否则平白拖满整个鸣牌窗口
   （实测：能碰的那家已经回了，却因为另一家"能吃但没点"而要等满 3 秒）。
   判据里的「压过」必须与实际仲裁**同一把尺子**（等级 → 座次；同级时离打牌者近的赢），
   否则提前收工会改变赢家。
3. **收工之后**（`Table.dropReplies` + 「type 必须属于本次询问」）：
   被取消询问的那家可能**回包已经上路**。这类回包没法用 `ask_id` 识别
   （老客户端根本不带 `ask_id`），却能：
   - 被下一次鸣牌询问按座位认领 → 凭空按了碰/吃；
   - 被下一巡的 `awaitAction` 当作出牌答复 → **玩家没动就被代打**。

   所以两手都要：取消时把**已在队列里**的废包摘掉（`dropReplies`），
   以及在认领处校验 **`type` 属于本次询问给过的选项** —— 废包的 `chi`/`pon`
   不可能出现在出牌询问的选项里，于是它被丢弃、玩家照样拿到完整 deadline。

### 报文只走 ASCII 码，文案归客户端

服务端是**唯一权威方**，但它**不负责措辞**。报文里的词汇性文本一律只发稳定 ASCII 码：

| 报文里 | 发什么 | 谁翻成中文 |
| --- | --- | --- |
| `yaku[].code`（+ 参数化役种的 `tile`） | `"riichi"` / `"yakuhai"` + `"5z"` | 客户端语言文件 `yaku.*` |
| `limit` | `"mangan"` / `"kazoe_yakuman"` | `limit.*` |
| `reason` | `"exhaustive"` / `"four_kans"` | `reason.*` |
| `error.code` / `error.arg` | `"unknown_cmd"` + `"frobnicate"` | `error.*`（模板带 `%1`） |
| 牌码 | `"1m"` / `"0p"` | `tile.*` |

- 码表集中在 `rules/YakuCodes.java`（中文名 → 码的**唯一**映射处）。`Evaluator` 内部照旧用中文名
  （日志与自测可读），只在 `Round`/`Table` 发报文时翻成码。
  **新增役种必须登记**，否则整场模拟的自检会因 `misses() > 0` 失败。
- 中文只留在三类**用户数据**字段：`seats[].name`（玩家名）、房间名、`chat.text`。
  这三类是不可枚举的，且本来就是"任意文本"。
- 客户端把码翻译成文案（`src/i18n/Lang.cpp`），**语言文件是独立的运行期资源**
  （`assets/i18n/<locale>.json`，目录优先 → qrc 兜底）→ **改文案不用重新编译**，
  加一门语言只是多一个 json。
- 这样分层的收益：报文可 grep / 可断言（`tools/e2e-test.mjs` 逐条审计非 ASCII），
  端到端不再依赖字符集，服务端也不必背一份"给玩家看的措辞"。

`tools/check-i18n.mjs` 是这条链路的**静态哨兵**：以服务端词表为权威，
逐码核对客户端语言文件有没有对应文案，缺一条即失败。

### 并发模型

- 每个连接一个读线程（`Session`），把 `cmd` 转成消息投递到该座位的阻塞队列。
- 每张桌子一个 `Table` 线程（游戏循环），串行推进状态机；所有状态修改都在该线程内，天然无锁。
- 需要等待玩家决策时，`Table` 调用 `seat.awaitAction(deadline)`，阻塞在队列上；超时按规则代打。
- 出站消息投给每个 `Session` 的写线程队列，避免慢客户端阻塞牌局。

### 牌面绘制

牌面走 **SVG 矢量素材**（`client/assets/tiles/<牌码>.svg`，38 个：37 种牌 + 牌背），
**取不到素材时回退到 `QPainter` 程序化绘制**——删掉整个 `tiles/` 也不会白屏：

- 查找顺序：exe 同级 `tiles/` → qrc 内嵌 `:/tiles/` → 程序化绘制。
- 换素材只需保持**文件名（= 牌码）与 `viewBox="0 0 300 400"`**，**改完重启客户端即生效，无需重新编译**。
- 只有 `TileRenderer` 感知素材，`TableView` / 牌河 / 副露 / 手牌等调用方完全无感。

回退路径（同时也是占位符的绘制基准）：

- 牌面：象牙白圆角矩形 + 单层描边（**扁平，无厚度层、无立体感**）。
- 万子：上部汉字数字（一~九），下部红色「萬」。
- 筒子：按点位排列的同心圆（1筒大圆带内圈，2~9筒按标准点位）。
- 索子：按点位排列的绿色竹节（1索画一只绿色鸟形）。
- 风牌：東/南/西/北 黑色大字；三元牌：白（蓝框空白）、發（绿）、中（红）。
- 赤五：数字/图案用红色。
- 牌背：深绿纯色 + 斜纹（无渐变、无厚度层）。

尺寸**由内容反推**（不是先定一个"好看的方块"再往里塞）：`TableView::computeLayout()` 先按盘内要放的
东西（宝牌指示牌行 = 5 张、四家点数、场次、立直棒）与盘外要留的东西（四家牌河各 3 行 + 余量）
算出风盘 `cw/ch`，再钳制到外圈预算（`盘半 + riverExtent ≤ 屏半 − 内边距 − 手牌厚`），最后把 `ch`
补到接近 `cw`。**牌河、手牌、副露的尺寸都由 `手牌宽 tw` 按固定比例推出**（牌河 0.798 / 宝牌 0.76），
不再随窗口高度单独缩放。完整不变的约定见 `AGENTS.md` §6「风盘尺寸必须由内容反推」。

## 关键规则取舍（默认配置，可在 rules 中改）

以《雀魂》默认规则为基准（见 `docs/PROTOCOL.md` §5）：

- 有食断、有后付（アリアリ）、有里宝牌、有杠宝牌、有赤宝牌 3 张。
- 采用两倍役满（大四喜、国士无双十三面、四暗刻单骑、纯正九莲宝灯）。
- 无头跳，也不采用三家和了流局（多人可同时荣和，按逆时针顺序依次结算）。
- 中途流局：九种九牌、**四风连打**、四家立直、四杠散了（三家和了未采用，多人可同时荣和）。
- 有击飞、有流局满贯、有包牌、禁止食替、不听罚符 3000。
- 人和默认关闭（`renhou: "off"`）。
- 无西入延长战（南4局结束即终局）。

## 验证策略

五层阶梯，从便宜到贵（完整命令与覆盖清单见 `AGENTS.md` §4）：

1. **L1 规则引擎自测**：`java -jar server/build/mahjong-server.jar --selftest` —— 役种、符数、**完整打点表逐格比对**、
   振听、流局条件、杠与岭上的账、**「吃」的合法性（顺子必须服务端自己验）**、**不听罚符零和**、
   **四杠散了的真值表**、**赤宝牌张数**、鸣牌仲裁，
   外加 3 次「4 机器人整场半庄」模拟的点数守恒。**当前 414 项全绿。**
2. **L2 客户端自检**：`client\dist\mahjong-client.exe --selftest client\build\st` —— 牌码双向、NDJSON、`TableModel`
   事件应用、风盘布局不变量（点数等距 / 得点框同理 / 宝牌行只占中间列 / 河区不压手牌 / 牌河超 18 张仍逐行）、
   自动开关判据与接线、结算面 4 种情形，并出图。**当前 401 项全绿。**
3. **L3 协议端到端**：起真服务端，跑 `tools/*.mjs`（e2e / timeout / clock / firstturn / riichi-stale /
   claim-priority / utf8 / check-i18n / i18n-scan / i18n-gen）。
4. **L4 假服务端定点复现**：`tools/mock-server.mjs` 直接把客户端推进到目标状态再截图（比等牌快得多）。
5. **L5 真机联调**：`--autoplay` 连真服务端打完东风战；`--demo --shot` 出 GUI 实拍。

### 结算界面的牌面示意（字体方案）

牌局中的牌桌走 **SVG 矢量素材**（见上）；**结算界面改走内嵌字体 + OpenType 连字**，两者互不影响。

- 字体 `I.MahjongJP.otf`（Unicode 麻将牌字形），只用 `liga` 特性，**默认生效**。
- `ResultDialog::schematicOf()` 把和牌数据拼成字体能识别的牌码串，
  用控制字符编码多行结构（`U+001F` 行间 / `U+001E` 标签 / `U+001D` 旁挂），
  渲染成「标签 + 牌面」多行：**手牌 / 宝牌指示牌 / 里宝指示牌**
  （数据全部来自既有 `agari` 事件字段，**未新增协议字段**）。
- 和了牌**不并进手牌**：用固定 44px 间隔（= 一个整牌位）空出一格单独摆。
  不靠空格凑宽度——字体空格的字宽并不等于一个牌位。
- **两种表示并存**：牌面示意在上，原文字结算在下；字体不可得或串含非法字元时
  只显示文字，**不会出现空白或错牌**。

为什么不用字体直接画牌桌：字体渲染的是**固定字形**，而牌桌需要按座位旋转、
区分手牌/副露/牌河并做避让布局，SVG + `QPainter` 变换更合适；结算是一次性静态展示，字体最省事。
